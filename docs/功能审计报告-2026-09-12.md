# 轻简音乐（qingjian-music）功能完备性审计报告

- 审计日期：2026-09-12
- 审计范围：`apps/mobile`（Expo SDK 57 / RN 新架构，expo-router）、`packages/core-domain`、`packages/provider-api`、`packages/provider-fnos`、`modules/*` 本地原生模块
- 审计方法：全量通读源码 + 交叉验证调用链（grep 确认「定义—调用—落地」三段是否齐备）+ 对照 `docs/fnos-music-api.md`、`docs/fnos-transcode.md`、`docs/design-tokens.md` 的实测记录
- 结论口径：**完成度**指「用户可感知的功能是否可用且闭环」，不指代码量。凡「有 UI 入口但无真实动作」「有能力声明但无实现」「有实现但无入口」均计为**断点**

## 0. 项目定位与架构基线

| 层 | 位置 | 职责 | 状态 |
| --- | --- | --- | --- |
| 领域层 | `packages/core-domain` | 纯类型与规则：实体、能力声明、分页、错误、队列、歌词、浏览节点 | 完整、无副作用，可复用 |
| 契约层 | `packages/provider-api` | `MusicProvider` 接口、`HttpClient`、`ProviderRegistry`、地址校验 | 完整，但**接口未覆盖歌单写操作** |
| 实现层 | `packages/provider-fnos` | 飞牛音乐私有 API（端点表 + zod schema + 映射 + FN ID 解析） | 完整度高，实测充分 |
| 应用层 | `apps/mobile` | expo-router 界面 + RNTP 播放内核 + 本地缓存/持久化 | 播放内核强，写路径弱 |
| 原生层 | `modules/{airplay-button,app-icon,system-volume}` | iOS 系统能力封装 | iOS 完整，Android 为桩 |

多后端（`emby` / `subsonic` / `demo`）仅在 `ProviderId` 枚举中占位，**未实现**；`reference/cymusic` 是 Apache-2.0 参考实现，不参与构建。

## 2. 功能管线闭环分析（输入 → 处理 → 输出 → 反馈）

### 2.1 已闭环的管线

**P1 登录接入**：输入（地址/FN ID/账号/密码）→ 解析与校验（`validateBaseUrl` + `fn-connect` 探测）→ 认证（sha256 登录）→ 持久化（Keychain）→ 反馈（错误文案分流 + 路由跳转）。**闭环完整。**

**P2 浏览检索（读）**：入口 → 分页列表 → 详情 → 点播。全链路有加载/空/错误态，**读路径闭环**。

**P3 播放主链路**：选曲 → `toQueueItem` → `toRntpTrack`（三选一：缓存本地文件 / 转码 HLS / 网络直推）→ RNTP → 系统媒体控制 → 起播上报 → 历史查询失效。**闭环完整且健壮**，异常路径（转码会话被回收、原生解码失败、冷启动恢复）均有兜底。

**P4 歌词显示**：请求（React Query 30min 缓存）→ 解析（增强型 LRC 逐词）→ 渲染（逐行/逐字/翻译）→ 交互（点击跳转、长按全屏、滑动恢复）。**显示闭环完整。**

**P5 自动缓存**：命中判断 → 写入（.part → move）→ 索引落盘 → 配额/LRU/首数淘汰 → 手动清理。**闭环完整。**

**P6 多服务器**：添加 → 切换（先建会话再清旧域）→ 删除（连带清凭证）。**闭环完整。**

**P7 漫游电台（自动）**：`radioStart` → 播放 → 队尾 `fillRadio` 续歌 → 会话重置。**自动链路闭环**，但缺 UI 主动控制（见下）。

### 2.2 存在断点的管线

| 管线 | 断点位置 | 后果 |
| --- | --- | --- |
| **歌单写管线** | 契约层无方法 → 实现层未写 → UI 无入口；`add-to-playlist` 只 toast | 用户**完全无法管理歌单**；「添加到歌单」是**假功能**，比缺失更危险（用户以为成功了） |
| **歌词偏移管线** | 输入（UI 入口）缺失 → hook `useLyricOffset` 已备但零调用 → 写回能力 `lyricOffsetWriteback` 不可达 | 能力声明与实际不符；服务端偏移字段永远不会被 App 写入 |
| **搜索联想管线** | 实现层 `suggest` 已就绪 → UI 零调用 | 已投入的实现白费；搜索体验退回纯关键词 |
| **收藏管线** | 输出面（列表/详情）缺失 → 仅播放域可触发 | 典型场景「浏览时随手收藏」不可用，必须先进播放页 |
| **离线下载管线** | 无下载入口 → 无下载队列 → 无离线列表 → 「已下载」页无输出面 → 「下载音质」无消费方 | 五段全断；用户无法主动离线，缓存是「被动副产品」 |
| **播放错误反馈管线** | 处理（强制转码重试）有 → 输出（用户提示）缺 → 反馈（重试/跳过）缺 | 播放失败时用户只看到卡住，无解释、无操作 |
| **首页数据管线** | 输出态缺失（无刷新、无错误态、失败静默空白） | 网络异常时首页「看起来是空的」，用户无法判断是没歌还是出错 |
| **队列清空管线** | 有 `clearQueue` 能力，队列页只提供「清历史」 | 用户无法一键清空待播列表 |
| **播放历史清理管线** | provider 有 `playHistory.delete` 端点 → 无接口方法、无 UI | 历史只能看不能清（服务端侧） |
| **漫游手动控制管线** | `radioNext/radioPrevious` 已实现 → 仅自动续歌用，UI 无「漫游上一首/下一首」 | `radioPrevious` 从未被调用（死路径） |

### 2.3 系统性根因：能力声明—接口—实现—UI 四层脱节

本项目有一处**结构性问题**：`Capabilities` 是一份很好的「功能开关」设计，但没有一致性校验机制，导致同一能力的四个层次各自漂移。

| 能力 | capabilities 声明 | 端点表 | 契约接口 | UI 入口 | 是否一致 |
| --- | --- | --- | --- | --- | --- |
| `playlists` | `'write'` | 有 5 个写端点 | **无写方法** | **无入口** | ❌ 四层脱节 |
| `searchSuggest` | `true` | 有 | 有 `suggest()` | **无调用** | ❌ 三层脱节 |
| `lyricOffsetWriteback` | `true` | 有 `event/report` | 有 `setLyricOffset()` | **无入口** | ❌ 三层脱节 |
| `transcode` | `true` | 有 | 有 `stream(allowTranscode)` | 无显式开关（自动） | ⚠️ 隐性 |
| `multiLibrary` | `true` | 有 `shared-library/list` | 无方法 | 无 | ❌ 仅声明 |
| `favorites` | `true` | 有 | 有 `setFavorite()` | **仅播放域** | ⚠️ 部分 |
| `radio` | `true` | 有 | 有 3 方法 | 仅自动续歌 | ⚠️ 部分 |

## 4. 整体功能完备性总结与改进方向

### 4.1 总结

**强项（已达可日常使用水准）**
- **播放内核**是全项目最扎实的部分：队列模型、转码兜底、缓存策略、持久化恢复、系统媒体集成、异常兜底，链路完整且有单测。这部分的设计密度明显高于行业同类个人项目。
- **认证与会话**：FN ID 解析 + 内外网探测 + 静默重登 + 多服务器，闭环且工程细节到位（单飞、顺序、回滚）。
- **消费型读路径**（浏览、搜索、详情、歌词显示）基本闭环，分页/加载/空/错误四态在多数列表页已规范。
- **文档化程度高**：`docs/` 三份实测文档把私有 API、转码时序、设计 token 来源都钉死了，可维护性好。

**弱项（结构性）**
1. **「生产型」能力几乎空白**：歌单管理、收藏入口、主动下载——这三类是音乐 App 的高频操作，目前**全部不完整**。其中歌单写与「添加到歌单」属**假功能**（能力声明了、端点有了、UI 弹了成功提示，但没有请求），这是最需要立刻修的一类问题。
2. **四层脱节**（capabilities / endpoints / interface / UI）缺乏机制约束，导致「实现完了但没人调用」（suggest、`useLyricOffset`、`radioPrevious`）与「声明了但没有实现」（playlists write、multiLibrary）同时存在。
3. **错误反馈闭环普遍偏弱**：多处失败只写 `console.warn`，用户侧无感知（播放失败、首页查询失败、预取失败）。
4. **工程债**：死代码、生产日志、源码字符串断言式测试、Android 未验证。

**完成度量化（按功能域）**

| 功能域 | 完成度 |
| --- | --- |
| 播放内核 | ~95% |
| 认证与会话 | ~90% |
| 浏览/详情（读） | ~85% |
| 歌词（显示） | ~85% |
| 设置与个性化 | ~70% |
| 搜索 | ~60% |
| 收藏 | ~55% |
| 离线/缓存 | ~45%（自动缓存 A，主动下载 D） |
| 歌单 | ~30%（读 A，写 D） |
| 车机 / 多后端 | ~5% |

### 4.2 改进方向

1. **先修「假功能」，再补「缺失功能」。** 假功能的危害大于缺失：用户以为成功，数据却没变。P0 的第 1、2、3 项应最先处理。
2. **把「能力声明」变成可执行的契约。** 为 `Capabilities` 增加一致性测试（能力为 true ⇒ UI 有可达入口；UI 入口 ⇒ 有真实实现），从机制上根治四层脱节。这是本报告认为**投入产出比最高**的一项改进。
3. **补齐「生产型」三件套（歌单 / 收藏 / 下载），把 App 从「能听」推到「能管」。** 当前 App 更像一个高完成度的播放器，而不是一个完整的音乐库客户端。
4. **建立统一的错误反馈层。** 把散落的 `console.warn` 收敛为「用户 toast + 可重试动作」，播放、列表、写操作三类分别定义反馈策略。
5. **明确产品边界再投入**：是否需要真离线（决定缓存是否要从 `Caches` 迁到 `Documents` 并做下载管理）、是否做多后端与车机（决定 `provider-api` 扩展节奏）。这两项会显著影响后续架构选择，建议先定调。
6. **清理工程债**：删死代码与生产日志、改造脆性测试、Android 至少跑通一次构建验证。
