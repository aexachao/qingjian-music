# 方案评估：本地解码 vs 服务端转码

- 日期：2026-09-13
- 问题：能否把「播不了的格式」的转码放到 App 本地做，让音乐后端退化成纯文件服务器，解码播放全在本地？
- 结论：**不建议做。** 收益面比直觉窄得多，而且被一个便宜得多的方案完全覆盖；成本却是量级上的差异。
- **替代方案已通过 spike 实测**（见 §8）：`init.mp4 + 按序分片` 拼接出的 FLAC-in-fMP4，AVFoundation 判定可播并**完整解码 1,323,000 帧无错** —— 不需要 FFmpeg、不需要任何原生代码。
- 前置文档：`docs/fnos-transcode.md`（转码实测）、`docs/设计补充2-真离线与外部歌词源-2026-09-12.md` §1.6（当时对「不可播格式离线」的取舍）

---

## 一、先说一个关键澄清：95% 的曲目**本来就是本地解码**

用户设想是「后端只做文件获取，解码放本地」。但看现在的实际链路（`player/controller.ts` 的 `toRntpTrack`）：

| 情况 | 现在的做法 | 解码在哪 |
| --- | --- | --- |
| 格式在白名单内（flac/mp3/m4a/wav/aac/alac/aiff/caf…） | `provider.stream()` 拿直链 → 交给 AVPlayer / ExoPlayer | **本地**（系统播放器） |
| 格式不在白名单（wma/ape/wv/dsd/tak/tta） | `POST /track/transcode` → HLS → 交给播放器 | 服务端 |

也就是说：**「后端只做文件获取 + 本地解码」已经是现状**，服务端唯一多做的一件事就是那 ~5% 的转码。

所以真正的问题只有一个：**要不要把那 5% 的转码也搬到本地。** 下面全部围绕这一点评估。

（量化依据：`apps/mobile/src/player/format-support.ts` 的注释记录了「实测这套曲库里 WMA 占了约 5%」；`docs/设计补充2` §1.6 也引用了同一个数字。）

## 二、技术可行性：三条硬约束

### 2.1 没有 WebAssembly —— JS/WASM 解码器这条路直接堵死

最省事的设想是「塞一个 ffmpeg.wasm 进去，纯 JS 解决、零原生代码」。**这条路在 RN 上不通**：

- RN 默认 JS 引擎是 Hermes，**Hermes 不支持 WebAssembly**（facebook/hermes#429 自 2020 年至今 open）。
- 想用 WASM 就得引入第三方 JSI WASM 运行时，那本身就是一个原生依赖 —— 「零原生代码」的卖点直接消失。
- 而且 ffmpeg.wasm 依赖多线程 + SharedArrayBuffer，RN 环境默认不具备。

**结论：本地解码 = 必然引入原生代码。** 这决定了后面所有的成本估算。

### 2.2 播放器不是我们的，也没有解码器注入点

| 平台 | 播放链路 | 能否注入自定义解码器 |
| --- | --- | --- |
| iOS | RNTP → SwiftAudioEx → **AVPlayer** | ❌ 无注入点 |
| Android | RNTP → **KotlinAudio v2.1.0** → **ExoPlayer 2**（`com.google.android.exoplayer2`） | ❌ 无注入点 |

Android 侧的证据（`node_modules/.../react-native-track-player/android/build.gradle`）：

```gradle
implementation 'com.github.doublesymmetry:kotlinaudio:v2.1.0'
```

播放器实例由 **KotlinAudio** 内部构造，`RenderersFactory` **没有对外暴露**。想挂 FFmpeg 解码器就得 fork KotlinAudio —— 不是改我们自己的代码，是维护一个第三方播放器库的分支。

另外注意：RNTP 用的是 **ExoPlayer 2（legacy `com.google.android.exoplayer2`）**，而官方 FFmpeg 解码扩展现在只维护 **Media3（`androidx.media3`）** 版本，且需要**自己用 NDK 编译 FFmpeg 源码**再打成 AAR（`lib-decoder-ffmpeg`，靠 `Class.forName` 被发现）。这条链在 ExoPlayer 2 上要额外做版本适配。

### 2.3 因此只剩一种可行的架构：**先解码成文件，再交给现有播放器**

```
不可播格式 → 原生解码器 → 写成一个 AVPlayer/ExoPlayer 能读的文件（FLAC/ALAC）
           → 把 file:// 交给 RNTP → 其余全部沿用现有实现
```

这是唯一不会把播放层推倒重来的做法。它的好处是**锁屏、控制中心、后台播放、AirPlay、CarPlay、进度、seek 全部保持原样**。

但它带来一个不可回避的代价：**必须先解码完才能起播**（没有流式）。除非再做「边解码边增长的文件」或「本地 HLS 服务」—— 那又是另一个量级的工程，而且恰好是我们刚花力气消除的那类「播放前必须等待某个异步前置步骤」的脆弱结构。

> 备选架构（自己写 PCM 播放引擎，AVAudioEngine / AudioTrack）等于重写整个播放层：锁屏、远程控制、后台、AirPlay 全部要重新实现。**不建议考虑。**

## 三、成本清单

### 3.1 一次性工程成本

| # | 项目 | 说明 | 量级 |
| --- | --- | --- | --- |
| 1 | **FFmpeg 双端构建** | iOS 出 xcframework；Android 用 NDK 交叉编译（arm64-v8a / armeabi-v7a / x86_64）。必须只开解码器、关编码器/滤镜/大部分封装，否则体积失控 | 大 |
| 2 | **本地原生模块 ×2** | 解码 + 落盘 + 进度/取消 + 清理。项目已有 3 个原生模块先例（`airplay-button`/`app-icon`/`system-volume`），结构可照抄，但这是最复杂的一个 | 中 |
| 3 | **可能的 KotlinAudio fork** | 若要走 ExoPlayer 渲染器路线；若走「解码成文件」路线则可避免 —— 这也是选后者的原因之一 | 中～大 |
| 4 | **临时文件生命周期管理** | 每首解码产物 25–300MB（见 §4），必须处理：解码中取消、播放完清理、App 被杀后的残留、磁盘不足 | 中 |
| 5 | **LGPL 合规** | FFmpeg 是 LGPL-2.1+（**绝不能** `--enable-gpl`）。上架 App Store 需动态链接 + 提供可重链接能力，是一套固定的合规动作 | 中 |
| 6 | **构建链可用性** | ⚠️ **本仓库本机没有 JDK / Android SDK**（见项目记忆）→ 引入的是一条**在本机完全无法构建、无法验证**的链路 | — |

### 3.2 持续性成本

- **包体积**：音频-only 的 FFmpeg 裁剪后，双平台双架构保守估计 **+15～40MB**（需实测，见 §7）。
- **每台设备的解码 CPU/电量**：DSD/APE 这类重解码在手机上不是免费的；服务端转码是「一次解码、多端受益」，本地解码是「每台设备各自付一遍」。
- **格式边角维护**：CUE 整轨切分、DSD 的 lsbf/msbf 变体、APE 高压缩档、损坏文件容错 —— 这些服务端 FFmpeg 已经处理好了，搬到本地就是我们的 bug 面。
- **双端行为不一致**：iOS 与 Android 的解码器版本/行为差异会成为新的「平台相关 bug」来源（这个仓库已经被 RNTP 的跨端差异坑过一次，见 `playback-error-policy.ts` 的说明）。

### 3.3 收益侧（要诚实列出）

| 收益 | 是否独有 |
| --- | --- |
| 不可播格式也能**离线播放**（不需要服务端参与） | ✅ 独有 |
| 省 NAS CPU（服务端每次播放都要重新转码，目前**没有缓存转码产物**） | ✅ 独有 |
| WMA 这类 lossy 源可省约 5× 网络带宽（见 §4） | ✅ 独有 |
| 减少对转码会话保活的依赖 | ⚠️ 部分 —— 会话可靠性已经修过了 |

## 四、按格式类别的量化对比

假设单曲 4 分钟；服务端转码输出为无损 FLAC（实测约 1000 kbps ≈ 125 KB/s → 4 分钟 ≈ **30MB**，依据 `docs/fnos-transcode.md` §0'）。

| 源格式 | 原始体积(4min) | 服务端转码流 | 本地解码需先下载 | 本地解码产物 | 本地是否更优 |
| --- | --- | --- | --- | --- | --- |
| **WMA**（lossy 192k） | ~6 MB | ~30 MB | ~6 MB | ~25–30 MB (FLAC) | ✅ 带宽省 ~5× |
| **APE / WavPack**（无损） | ~25 MB | ~30 MB | ~25 MB | ~25–30 MB | ➖ 基本打平 |
| **TAK / TTA**（无损） | ~25 MB | ~30 MB | ~25 MB | ~25–30 MB | ➖ 基本打平 |
| **DSD64** | ~170 MB | ~30 MB | ~170 MB | **~250 MB (PCM 176.4/24)** | ❌ **明显更差** |

几个要命的点：

1. **本地解码只对 lossy 源有带宽优势**，而无损源打平、DSD 明显更差。而 WMA 恰好就是那 5%。
2. **DSD 是病态案例**：源 170MB、解码产物 250MB、还必须先整首下载完。服务端转码输出只要 30MB。这里本地解码在**带宽、磁盘、等待时间**三个维度全输。
3. **解码产物比源文件更大**是常态（无损源 → PCM/FLAC 基本不缩小；lossy 源 → 无损输出反而变大）。所以「本地解码省流量」只在「下载 lossy 原始文件」这一种组合下成立。
4. 无论哪种格式，本地解码都多了一个**「必须解码完才能播」的等待**，而服务端转码是边转边播。

## 五、为什么「缓存服务端转码产物」是更优解

上面列的三个独有收益里，有两个（**省 NAS CPU**、**不可播格式离线**）不需要写一行解码器就能拿到：

> 把服务端转码出来的 HLS 产物**缓存成单文件**，存进本地缓存/离线目录。

为什么可行且比想象的简单：

- 该 m3u8 是 **VOD 播放列表**（`#EXT-X-VERSION:7` + `PLAYLIST-TYPE:VOD` + `#EXT-X-MAP:URI="init.mp4"` + `#EXT-X-ENDLIST`），**不是直播流**，所以「拉全部分片」这件事有确定的终点。
- 分片是 **fMP4**，结构是 `init.mp4` + 顺序编号的分片。按顺序拼接 `init.mp4 + seg0 + seg1 + …` 得到的就是一个合法的 fragmented MP4，AVPlayer / ExoPlayer 都能当**本地文件**直接播。
- 没有加密（无 `#EXT-X-KEY`），不需要处理密钥。

所以工作量是：解析 m3u8（几十行的文本格式）→ 按序下载 → 字节拼接 → 存盘 + 索引。**这是一个纯 JS 的、可单测的任务**，不需要任何原生代码。

> 与 `docs/设计补充2` §1.6 的关系：当时把「下载后拼接分片」判为「易错、性价比低」，那是在**离线下载**的语境下评估的 —— 要求用户可见的下载管理、可暂停续传、失败可解释。如果只当作**播放缓存**（失败就丢弃、回落网络、不进用户可见的离线列表），风险小得多。**建议重新评估，值得一个半天到一天的 spike。**

拿到它之后：

| 收益 | 本地解码方案 | 缓存转码产物方案 |
| --- | --- | --- |
| 不可播格式离线播放 | ✅（需下载原始文件 + 每次解码） | ✅（一次缓存，直接播） |
| 省 NAS CPU | ✅ | ✅（只转一次） |
| WMA 省 5× 带宽 | ✅ | ❌（仍走服务端转码） |
| 需要原生代码 | 必须 | **不需要** |
| 需要 FFmpeg / LGPL 合规 | 必须 | 不需要 |
| 包体积增加 | +15～40MB | 0 |
| 起播延迟 | 必须先解码完 | 同现状（边转边播） |
| 本机可否开发验证 | ❌ 无 Android 环境 | ✅ 纯 JS，可单测 |

**唯一留在本地解码那边的是「WMA 省 5× 带宽」这一条。** 为了 5% 的曲目、在单一维度上省一点带宽，去引入 FFmpeg + 双端原生模块 + LGPL 合规，性价比明显不成立。

## 六、结论与建议

### 6.1 建议

**不做本地解码。** 按性价比排序做这三件事：

1. **（已做）修好服务端转码路径的客户端可靠性** —— 本次会话已修复：串行队列看门狗、`ensurePlayer` 不再缓存失败、错误归因、转码超时对齐参考实现（15s→20s）、会话超时 3s。这几项才是近期「播不出来」的真实原因，成本是本地解码方案的约 1%。
2. **（建议做，半天～一天 spike）缓存转码产物** —— 按 §5 的拼接思路，先只当缓存、失败即丢弃。做成之后 NAS CPU 与不可播格式离线两个真问题同时解决。
3. **（可选）实测服务端是否已有更省事的能力** —— `docs/fnos-music-api.md` 的 recon 里出现过 `/stream/audio` 与 **`/stream/pcm`** 两个端点，但**从未实测**，也不在 `FNOS_ENDPOINTS` 里。如果 `/stream/pcm` 真能按参数输出 PCM/转码流，可能又是一条更省事的路。**注意**：即使存在，它仍然是服务端解码（CD 质量 PCM 约 1411 kbps，比现在的 FLAC 输出更费带宽），**不改变本结论**。

### 6.2 什么情况下应该重新考虑本地解码

给出触发条件，避免以后凭感觉反复讨论：

- 不可播格式占比从 ~5% 升到 **>20%**；或
- 缓存转码产物已经做了，NAS CPU 仍是瓶颈（即瓶颈不是「重复转码」而是「转码本身」）；或
- 出现**硬需求**：「完全离网也要能播全部曲库」，且不接受服务端预转码；或
- 需要支持一个服务端 FFmpeg **也解不了**的格式。

即使触发，也建议：**只做 iOS 先行**（xcframework 比 NDK 交叉编译简单得多）、**只针对 WMA 这类小体积 lossy 格式**、**明确不支持 DSD**（§4 已证明 DSD 本地解码全维度更差）。

### 6.3 一个更根本的判断

这次评估最有价值的结论不是「本地解码不行」，而是：

> **「服务端转码」这条路本身没有问题，出问题的是我们客户端对它的使用方式。**

近期所有「播不出来」的故障，根因都在客户端（错误字段读不到、队列被悬挂任务堵死、超时比参考实现还短、会话标记单向不可逆）。把这些修完之后，服务端转码的剩余成本只有「NAS CPU」和「不可播格式无离线」—— 而这两项都有一个**不含任何原生代码**的解法。

在评估「要不要换架构」之前，先把现有架构用对，这个顺序很重要。

## 八、Spike 实测结果（2026-09-13，已完成）

**结论：§5 提出的「缓存转码产物」方案，核心假设已在本机验证通过 —— 拼接出的文件 AVFoundation 能播、能完整解码。**

### 8.1 方法（可复现）

用 ffmpeg 以**与飞牛转码相同的参数**生成同形状的样本，避免依赖真实服务器：

```bash
# FLAC-in-fMP4 的 VOD HLS：init.mp4 + 2 秒分片 + ENDLIST，与 docs/fnos-transcode.md 记录的实测形状一致
ffmpeg -f lavfi -i "sine=frequency=440:duration=30" -f lavfi -i "sine=frequency=660:duration=30" \
  -filter_complex "[0:a][1:a]amerge=inputs=2[a]" -map "[a]" \
  -c:a flac -ar 44100 -ac 2 \
  -f hls -hls_segment_type fmp4 -hls_time 2 -hls_list_size 0 -hls_playlist_type vod \
  -hls_fmp4_init_filename init.mp4 -hls_segment_filename "seg%d.m4s" preset.m3u8
```

生成的播放列表与飞牛产物形状一致（`#EXT-X-VERSION:7` / `PLAYLIST-TYPE:VOD` / `#EXT-X-MAP:URI="init.mp4"` / 2 秒分片 / `#EXT-X-ENDLIST`）。

新增两个工具（都在仓库里，可复跑）：

| 文件 | 作用 |
| --- | --- |
| `scripts/spike/transcode-concat.ts` | `local` 模式做本地拼接验证；`remote` 模式对着真实服务器走完整流程（转码 → 心跳 → 下载 → 拼接 → quit） |
| `scripts/spike/verify-avfoundation.swift` | 用 **AVFoundation**（iOS 上 RNTP 的真实播放框架）判断能否播放并**完整解码** |

### 8.2 结果

拼接逻辑本身：`init.mp4 + 15 个分片` → 733,140 bytes，顶层 box `ftyp:1 moov:1 styp:16 sidx:15 moof:15 mdat:15`，`moof/mdat` 配平。

AVFoundation 验证（正常路径）：

```
isPlayable            : ✓ true
duration              : 30.0 秒
期望时长              : 30.104 秒（偏差 0.104）✓
audio tracks          : 1
  codec               : flac 44100Hz 2ch
AVAssetReader         : completed，解出 163 个缓冲区 / 1323000 帧
✓ 通过：AVFoundation 可以播放并完整解码该文件
```

`1323000 帧 = 30.0s × 44100Hz`，**一帧不差、无解码错误**。`ffprobe` 独立复核一致（`codec_name=flac`、`duration=30.0`、全量解码退出码 0）。

→ **`init.mp4 + 按序分片` 拼接得到的 FLAC-in-fMP4 文件，AVFoundation 认、能完整解码。**
→ 也就是说：**这条路线不需要 FFmpeg、不需要任何原生代码。**

### 8.3 负面对照：验证方法本身有没有牙

一个「永远通过」的验证等于没有验证。所以刻意构造了两种坏文件：

| 对照 | ffprobe | AVFoundation | 结论 |
| --- | --- | --- | --- |
| **漏掉 init.mp4** | `Invalid data found when processing input` | `isPlayable = false`、0 轨道、时长 0 | ✅ 能抓到 |
| **分片倒序** | 只报 `duration=2.089796`（静默） | **`isPlayable = true`**、时长 1.996 秒 | ⚠️ 只有时长交叉校验能抓到 |

**这是本次 spike 最有价值的发现**：

> 分片顺序错时，文件**仍然 `isPlayable = true`、仍然能解出 88,056 帧**。
> 也就是说「能不能打开 / 能不能播」这类检查**完全兜不住顺序错误** ——
> 用户会得到一个「能播、但只有 2 秒、而且内容是错的」文件，属于静默损坏。

### 8.4 对生产实现的直接要求（由 spike 得出，不是推测）

1. **必须做时长交叉校验**：用播放列表 `Σ EXTINF` 与产物实际时长比对，偏差超阈值就丢弃缓存并回落网络。只检查「能否播放」不够（见 8.3）。
2. **下载期间必须持续发心跳**（每 10 秒）。服务端按心跳判活，断掉约 1 分钟后任务被回收、分片开始返回 **410**。一首 4 分钟曲目约 30MB / 120 个分片，下载过程足以踩到这个坑。`transcode-concat.ts` 的 `remote` 模式已经实现了这一点。
3. **拼接必须严格按播放列表顺序**，不能用并发完成的顺序。并发下载可以，但**落盘顺序**要按 index 排。
4. **只缓存 `#EXT-X-ENDLIST` 的列表**。没有 ENDLIST 说明是滚动窗口，产物不完整 —— `parseHlsPlaylist` 会把 `isComplete` 报成 false，调用方必须放弃。
5. **遇到加密或按字节区间的列表要显式失败**，不能"尽力拼一个"。`hls-playlist.ts` 已对 `#EXT-X-KEY` / `#EXT-X-MAP` 带 `BYTERANGE` / 分片缺 `#EXTINF` 三种情况抛 `UnsupportedPlaylistError`。
6. **产物后缀必须写 `.mp4`，绝不能沿用源格式后缀。** 见 §8.4.1 —— 这是本方案最容易踩、且失败得最难查的一个坑。

### 8.4.1 产物后缀：一个必然踩的坑（实测）

容器是 **fragmented MP4**，里面的编解码是 **FLAC**。所以后缀该按**容器**取，不是按编解码取。

实测方法：把**同一份字节**复制成不同后缀，逐个用 AVFoundation 验证。

| 后缀 | `isPlayable` | 说明 |
| --- | --- | --- |
| `.mp4` / `.m4a` / `.mov` | ✅ true | 正确写法（同族容器） |
| `.flac` / `.mp3` | ✅ true | 靠**内容嗅探**侥幸通过，但走了另一条解析路径 —— 时长读数从 30.000 变成 30.093，说明解析器不同，不可依赖 |
| `.wma` / `.ape` / `.dsf` / `.dff` / `.wv` / `.tak` / `.tta` | ❌ **false** | 时长 0、无音频轨道，直接不可播 |

**要命的地方**：播不了的那组后缀（`.wma`/`.ape`/`.dsf`/`.dff`/`.wv`/`.tak`/`.tta`），**恰好就是需要转码的那组源格式**。

而现有缓存命名 `cacheFileName(serverId, trackId, item.format)` 用的正是**源格式**后缀 —— 也就是说，如果实现时直接复用它，结果是**必然 100% 失败**，而且失败形态是「文件内容完全正确、就是播不出来」，最难排查。

已固化为代码约束（`apps/mobile/src/player/audio-cache-policy.ts`）：

```ts
export const TRANSCODE_CACHE_FORMAT = 'mp4'
export function transcodeCacheFileName(serverId, trackId): string  // 转码产物专用命名
```

用独立命名还带来一个好处：**同一首歌的原始文件与转码产物后缀不同，可以共存、不会互相覆盖**（`srv_track.wma` vs `srv_track.mp4`）。

> 附带确认：`afinfo` 报告该文件 `File type ID: mp4f`（fragmented MP4）、`Data format: ... flac ... 44100 Hz` —— 容器与编解码的判断一致。

### 8.7 真实服务器实测（2026-09-13 补充，结论已从「样本」升级为「真机数据」）

对真实 NAS（192.168.2.100）跑通了完整流程。**§8.5 的未验证项 1–4 全部关闭**。

库内 41193 首，需要转码的占 **7.5%**：

| 格式 | 数量 | 占比 | 规格 | 转码+拼接结果 |
| --- | --- | --- | --- | --- |
| `flac` / `wav` / `mp3` / `m4a` / `aiff` | 36986 | 89.8% | — | 原生可播，不走转码 |
| **`wma`** | **2830** | **7.1%** | wmav2 2ch 44.1kHz | ✅ 5s / 23MB |
| **`dts`** | **146** | 0.4% | dts **6ch** 48kHz | ✅ 6s / 44MB |
| **`dff`** | **24** | 0.1% | dsd_msbf 352.8kHz | ✅ 10s / 273MB |
| **`dsf`** | **13** | 0.0% | dsd_lsbf_planar 705.6kHz | ✅ 16s / 203MB（见下） |
| **`ape`** | **1** | 0.0% | ape 2ch | ✅ 5s / 18MB |

5 种需转码格式**全部通过** AVFoundation 验证（`isPlayable = true` + 完整解码 + `moof` 计数与播放列表一致）。

**样本补齐后追加验证（同日）**：`tta`（31 片 / 60.0s）、**6 声道 FLAC**（31 片 / 60.1s，产物保持 6 声道）、
**CUE 整轨**（30 片 / 60.08s，服务端正确切出第 1 轨的 60 秒）也都通过。

由此得到两条对方案有价值的结论：

1. **CUE 整轨可用** —— 整轨 + 同名 `.cue` 被识别成多个 `isCue = true` 的轨道，
   且服务端能按 guid 切出单轨时间范围。所以「整轨镜像」这类资源也能走同一条缓存路径。
2. **多声道不会被服务端降混**（6ch 进、6ch 出），所以「原生直推 5.1 失败」时**回落转码是通的**。
   但原生直推本身行不行需要真机确认（AVPlayer / ExoPlayer 一般会自动降混）——
   **在有证据之前不要为多声道强制转码**，否则 5.1 专辑每次都要白转一遍。

⚠️ `wv`（WavPack）样本未被服务端索引（`/track/list` 与格式分布里都没有），
怀疑是扫描器不支持该扩展名（`tta` 这种同样冷门的格式能被索引）。待确认。

> 附带确认了两件事：**真实分片命名是 `00000.m4s`**（5 位补零，与本地样本的 `seg0.m4s` 不同 —— 所以必须从播放列表读名字，不能猜）；**`dts` 是 6 声道**，正是「多声道」这类边界情况的真实样本。

#### 8.7.1 新发现：分片存在「还没生成」的竞态（生产必须重试）

`POST /track/transcode` 返回 `status:'success'` **只代表任务已建**，分片可能还没生成 —— 此时请求分片返回 **404**，而播放列表与 `init.mp4` 都能正常取到，现象很迷惑。

- 触发条件与源文件解码/编码量正相关：`wma`（7MB）几乎不失败；`dsf`（DSD256，314MB）**稳定复现**，等待约 2 秒后全部 200。
- 这是**朴素顺序下载实现必踩的坑**，而 web 端因为用 hls.js（自带重试）不会暴露。
- 生产实现要求：**对 404 做有界重试**（404 = 未生成；410 = 任务被回收，需重开会话）。`transcode-concat.ts` 已实现。

#### 8.7.2 新发现：完整性判据要用「分片计数」，不能只用时长

`dsf` 那条曲目：源 DSD256（705600Hz），服务端重采样成 **384000Hz**（非整数比 1.8375），产物 232.1s 而源 233.7s（**短 1.65 秒**），且容器时长元数据（232.1）与可解码音频（231.05）不一致、末尾有时间戳跳变（230.997 → 232.000）。

**这不是拼接引入的** —— 产物 `moof` 数 = 117，与播放列表 117 片完全一致，一片不漏、顺序正确。同一份数据在 App 里走 HLS 也会如此，属服务端既有行为。

由此得出**两条判据都必须做**：

| 判据 | 抓什么 | 为什么不能只用另一个 |
| --- | --- | --- |
| `moof` 数 == 播放列表分片数 | 丢片 / 重复（**精确**） | 时长抓不住：漏一个 2s 分片在 4 分钟曲目里只占 0.8% |
| 产物时长 vs 源时长 | 顺序错误 / 静默损坏 | 计数抓不住：倒序时分片数不变，但时长从 30s 变成 2s |

**而且时长容差不能设太紧**（如 0.5s）：服务端的重采样误差本身就能到 1%，会把正常产物误判成失败。建议「计数严格 + 时长宽松（±5%）」。
