# 设计梳理：歌单写入 / 快捷菜单上下文 / 歌词匹配

- 日期：2026-09-12
- 关联：`docs/功能审计报告-2026-09-12.md`（本文是对该报告 P0/P1 项的细化设计）
- 结论速览：
  1. **歌单新增完全可以在 App 内实现**（端点、权限、错误码都已确认），建议一期只做「新增 + 添加到歌单接真 + 改名/删除」，导入放二期。
  2. **快捷菜单目前是"上下文无关"的**：待播行没有菜单，列表行的菜单**完全没有播放队列操作**。需要按「列表 / 待播 / 正在播」三上下文动态组装。
  3. **歌词不是"缺功能"，而是"选错了"**：服务端本来就返回多版本歌词，但 App 只取 `preferred` 或数组第一条，没有按"逐字 > 整行 > 纯文本"择优，也没有本地缓存。这条属于**修 bug 级收益**。

## 一、歌单：现状核实、可行性、分期方案

### 1.1 现状核实

**读路径已闭环**

- 契约：`playlists()` / `playlistTracks()`（`packages/provider-api/src/provider.ts:75-76`）
- 界面：`apps/mobile/src/screens/playlists.tsx`、`playlist-detail.tsx`（复用 `TrackListScreen`）
- 空态文案：「还没有歌单，可以在飞牛音乐网页端创建」（`playlists.tsx:35`）——等于承认写路径缺失

**写路径三层全缺**

| 层 | 状态 |
| --- | --- |
| 后端端点 | ✅ 已登记（`provider-fnos/src/endpoints.ts` playlist 段） |
| 契约接口 | ❌ `MusicProvider` 无任何歌单写方法 |
| fnos 实现 | ❌ 未实现 |
| UI 入口 | ❌ 无；`add-to-playlist` 只弹 `toast('已添加到歌单')`（`components/track-more-button.tsx:112-113`、`player/player-deck.tsx:476`） |
| 能力声明 | ⚠️ 已声明 `playlists: 'write'`（`provider-fnos/src/provider.ts:79`）——**声明与实际不符** |

### 1.2 可行性结论：**可以，在 App 内实现新增没有障碍**

依据（来自 `docs/fnos-music-api.md` 第 72-99 行的实测/静态分析）：

- 端点与参数已确认：`POST /playlist/create {name, coverId}`，`name` 长度 1-32，歌单上限 99999
- **权限不是障碍**：member 角色即可读写歌单（`AdminRequired=100003` 只用于库/用户管理）
- 错误码明确：`160001` 名称重复 / `160002` 达到上限 / `100002` 参数非法 / `100005` 不存在
- **不需要新原生能力**：纯 HTTP 写操作

需要新增的工程件：

- 一个**文本输入弹窗**：现有 `confirm-modal.tsx` 只有 title/message/按钮（`ConfirmOptions` 无自定义内容），不支持输入 → 需新增 `PromptModal`（或给 ConfirmModal 加 `input` 选项）
- 契约层方法与 fnos 实现

**风险与待实测**（写路径无法用 GET 探测，nginx 的 SPA fallback 会对任意未命中路由返回 200 HTML，所以必须真发 POST 才能确认）：

1. `POST /playlist/create` 成功响应体结构（只有 `guid` 还是完整 playlist 对象）→ 建议 zod 用宽松 schema 兜底
2. `coverId` 是否允许为空 / 省略
3. `add-track` 的 `trackGUIDs[]` 单次上限

建议：先在**测试账号**上跑一次真实 POST 验证，再写正式实现。

验收标准：

- 能在 App 内新建歌单，返回列表可见（不依赖网页端）

### 1.4 二期：歌单导入

**你的判断是对的**：导入解析放 App 内做，本质就是「create + 批量 add-track」。

建议按格式分期推进（难度与风险递增）：

| 阶段 | 格式 | 说明 |
| --- | --- | --- |
| 2a | **M3U / M3U8** | 最标准，`#EXTINF:时长,艺术家 - 标题` + 路径行，信息最全，匹配率最高 |
| 2b | **纯文本歌单** | 每行「歌名 - 歌手」或「歌名」，容错解析 |
| 2c | 第三方平台分享链接 | 需额外抓取页面/接口，**有版权与稳定性风险**，最后做 |

**匹配策略**（核心难点）：

1. 精确匹配：标题 + 艺术家全等（规范化后）
2. 次优：标题 + 专辑
3. 模糊兜底：标题规范化 + 时长容差 ±3s 消歧
4. 标题规范化规则：去 `feat.` / `ft.` / `(Live)` / `(Remaster)` / `[320K]` 等噪声后缀、统一全半角、统一大小写
5. 检索入口：`searchTracks(标题)` 取候选 → 本地打分排序；标题过短或候选为空时回落到 `tracks()` 全库分页（41193 首，代价高，需限流）

**必须让用户知道的硬约束**（来自实测）：

> 后端**没有任何 reorder / move-track / sort / import / export / m3u 端点**。歌单内顺序只由 `trackAddedAt` 递增决定。
> 因此导入的"顺序"只能是「按导入顺序追加」的**近似**，**无法持久化用户手工调整的顺序**。

这条要写进导入页的说明文案，否则用户会认为"导入后顺序乱"是 bug。

**其他设计要点**：

- **批量提交**：`add-track` 支持数组，按 100/批提交（对齐 `batch-detail` 的批次量级，实际上限待实测）
- **去重**：导入前用 `playlistTracks` 拉现有 guid 集合做差集，避免重复追加
- **未匹配项必须可见**：给一份「未匹配清单」（可复制/分享），而不是静默丢弃 —— 这是导入功能的反馈闭环，也是用户最在意的部分
- **进度反馈**：导入是长任务（几百首 × 分批请求），需要进度条 + 可取消 + 失败续传
- **失败回滚**：歌单已建但全部匹配失败时，提示用户是否删除这个空歌单

## 二、快捷菜单：从"上下文无关"改为"上下文感知"

### 2.1 现状核实

项目里有**两套菜单实现**，条目几乎相同：

| 组件 | 使用场景 | 条目 |
| --- | --- | --- |
| `TrackMoreButton`（`components/track-more-button.tsx`） | 列表行 / 搜索结果 / 详情页 | 添加到歌单、分享歌曲、歌曲信息、前往专辑、查看艺术家 |
| `DeckMoreButton`（`components/player/player-deck.tsx:273`） | 播放页底部 + 队列页当前卡 | 上述 + 分享歌词 |

两套菜单**都不含**：收藏、下一首播放、加入队列、下载。

`add-to-playlist` 在两套里都是假 toast（`track-more-button.tsx:112`、`player-deck.tsx:476`）。

### 2.2 回答你的两个问题

**Q1：已经在播放列表的歌曲，快捷菜单够吗？——够一半。**

- **队列当前卡**：有独立心形收藏按钮 + 完整菜单，基本够用。缺「从队列移除」（当前曲不允许删，这是有意设计，合理）。
- **队列待播行**：**只有左滑删除，没有「···」菜单**。所以缺「下一首播放」「移到队首」「收藏」「查看专辑」「歌曲信息」。
  - 现状：待播行唯一的操作是"删掉它"，用户想"把它挪到下一首"只能一路拖拽。

**Q2：不在播放列表的歌曲，菜单是否缺失？——是，而且缺得更关键。**

- 列表行菜单里**没有任何播放队列操作**：不能「下一首播放」、不能「加入队列」、不能「稍后播放」。
- 用户唯一能做的是**点整行 = 立刻替换整个播放队列并开始播放**。
- 这是最反直觉的地方：**想"排个队"必须先中断当前播放**。
- 值得注意：控制器其实**已经有 `appendTracks`（队尾追加）**（`player/controller.ts:196`），但**只给漫游续歌用，没有 UI 入口**；「下一首播放」（插到当前之后）需要新增函数。

### 2.3 建议：按「上下文 + 是否在队列中」动态组装菜单

定义三个上下文：

- **A. 列表 / 详情 / 搜索结果**（不在队列）
- **B. 队列待播行**（在队列，未播放）
- **C. 队列当前卡 / 播放页**（正在播）

条目矩阵：

| 菜单条目 | A 列表 | B 待播行 | C 当前曲 | 落地方式 |
| --- | :---: | :---: | :---: | --- |
| 下一首播放 | ✓ | ✓ | — | **新增** `playNext(tracks)` |
| 加入队列（队尾） | ✓ | — | — | **复用已有** `appendTracks`，只需接 UI |
| 从队列移除 | — | ✓ | — | 复用 `removeFromQueue` |
| 移到队首 | — | ✓ | — | 复用 `moveInQueue` |
| 收藏 / 取消收藏 | ✓（新增） | ✓（新增） | 已有独立按钮 | 复用 `useToggleFavorite` |
| 添加到歌单 | ✓ | ✓ | ✓ | 一期接真 |
| 下载（二期） | ✓ | — | ✓ | 依赖下载功能 |
| 分享歌曲 | ✓ | ✓ | ✓ | 已有 |
| 分享歌词 | — | — | ✓ | 已有 |
| 歌曲信息 | ✓ | ✓ | ✓ | 已有（目前只 toast，可升级为信息页） |
| 前往专辑 / 查看艺术家 | ✓ | ✓ | ✓ | 已有 |

**关键设计点**：

1. **`playNext` 需要新增**（控制器现有函数里没有"插到当前之后"）：
   - 语义：把曲目插入 RNTP index 1、store `queue` index 1，同步 `baseQueue`
   - 复用 `toRntpTrack` 生成播放地址，复用 `queueMutations` 串行化
   - 边界：队列为空时等价于 `playTrackList`；`playbackEnded` 状态下插入应清除该标记
2. **合并两套菜单**：抽成 `useTrackMenuActions(context)` 返回条目定义，`TrackMoreButton` 与 `DeckMoreButton` 共用，避免继续漂移（现在两套的 iOS/Android 分支已经各写了一份，改动要改四处）
3. **菜单反映队列状态**：已在队列中的曲目，「加入队列」应显示为**禁用态 +「已在队列中」**，避免重复添加 —— 这是反馈闭环
4. **待播行加「···」入口**：目前只有左滑（可发现性差），建议长按或行尾「···」出菜单，左滑保留为快捷删除
5. **播放页 Deck 菜单补「音质」「歌词偏移」**（与审计报告 P0 第 3 项合并做）

## 三、歌词匹配：多版本择优 + 本地优先

### 3.1 现状核实（本次最重要的发现）

**服务端返回的是"歌词条目数组"，不是一条歌词**

`/lyric/list?trackGUID=` 的响应（`packages/provider-fnos/src/schemas.ts:132-147`）：

```
{
  list: [{ guid, content, source, isLRC, offset, createdAt, updatedAt }, ...],
  preferred?: string   // 服务端指定的首选 guid
}
```

**但 App 的选法很粗暴**（`packages/provider-fnos/src/mappers.ts:194-207` `mapLyricSheet`）：

```ts
const picked = usable.find((entry) => entry.guid === preferredGuid) ?? usable[0]!
```

即：**优先 `preferred`，否则直接取数组第一条**。

**结论**：如果一首歌在服务端同时有「普通 LRC」和「逐字 LRC」两个条目，而数组第一条恰好是普通 LRC，App 就会用普通 LRC —— 用户能明显感觉"这首歌明明有逐字歌词但没生效"。**这正是你直觉指出的问题，且它属于 bug 而非缺功能。**

**补充事实**：

- `isLRC` 只表示"是否带时间轴"，**不区分逐字 / 整行**；要判断是否逐字，只能解析 `content` 看 `words` 是否非空
- `source` 字段（数字）含义未知，可能编码了"逐字 / 翻译 / 罗马音"等类型
- **本地歌词缓存不存在**：歌词只走 React Query 内存缓存（`staleTime: 30min`，`lib/lyric-offset.ts:29`），杀进程即失效

### 3.2 匹配机制设计（把你的思路形式化）

两个维度：**质量档（外层）× 来源（内层）**。

**档位定义**（由高到低，靠解析结果判定）：

| 档 | 名称 | 判定条件 |
| --- | --- | --- |
| T1 | 逐字 | `lines.some(l => l.words && l.words.length > 0)` |
| T2 | 整行 | `synced === true` 且无逐字 |
| T3 | 纯文本 | `synced === false` |
| T4 | 无歌词 | 无可用条目 |

**匹配顺序**（严格按你的描述）：

```
for tier in [T1, T2, T3]:
    本地缓存有该 tier  →  用它
    否则 API 候选里有该 tier  →  用它，并写回本地缓存
否则 → T4 无歌词（UI 显示「暂无歌词」，而不是空白区域）
```

**实现落点**：把 `mapLyricSheet` 从「挑一条」改成「**解析全部候选 → 按 tier 分组 → 返回最优 + 备选列表**」。

建议扩展领域模型（`packages/core-domain/src/lyrics.ts`，加可选字段，向后兼容）：

```ts
export type LyricTier = 'word' | 'line' | 'plain'

export interface LyricSheet {
  // ...现有字段
  tier: LyricTier
  /** 同一首歌的其他可用版本，供 UI 提供「切换歌词」 */
  alternates?: { id: string; tier: LyricTier; source?: string }[]
}
```

**性能注意**：API 一次请求就返回全部候选，所以**一次请求即可完成三个档位的判定**，不需要按 tier 发多次请求（否则会产生 N 倍请求）。"本地优先"只影响**是否发请求**，不影响请求次数。

### 3.3 本地优先的落地方式

新增 `apps/mobile/src/lib/lyric-cache.ts`，仿 `player/audio-cache.ts` 的 `expo-file-system` 用法（SDK 57 的 `Paths` / `Directory` / `File` API，见 `audio-cache.ts:1,44-51`）：

- 目录 `lyrics/`，文件名 `{serverId}__{trackId}__{tier}.lrc`
  - **tier 入文件名**是设计要点：天然支持"先找本地 T1，再找本地 T2"，不需要读文件内容就能判断档位
- 索引 `index.json`：记录 `tier`、`fetchedAt`、`lyricId`、`offsetMs`（偏移要一起缓存，否则离线时偏移丢失）
- 上限与淘汰：歌词文件极小（几 KB），建议按**条数**上限（如 2000 首）+ LRU，而不是按体积
- 存储位置：用 `Paths.cache` 即可（歌词可重新获取，不需要 `Documents` 的持久保证）

**与现有代码的衔接**：`useLyricSheet`（`lib/lyric-offset.ts:28-36`）内部改为「读缓存 → 未命中拉 API → 择优 → 写缓存」，**对外接口不变**，`lyric-view.tsx` 与 `player-deck.tsx` 无需改动。

### 3.4 关于「歌词匹配」的第二种理解：外部歌词源匹配

如果你的"歌词匹配"还包括「服务端没有歌词时，去外部（LRCLIB / 网易云 / QQ 音乐等）按歌名+歌手+时长匹配」：

- **技术可行**：新增 `LyricSource` 抽象（与 `MusicProvider` 平行）+ 匹配算法
- **但有三个风险**：第三方歌词版权、接口稳定性、匹配错误率高（同名不同版本）
- **建议放二期**，且约束为：
  1. **只补空缺**：服务端无歌词时才触发，**不覆盖**已有歌词
  2. **必须给纠正入口**：匹配错误时用户能手动换一条 / 重新搜索 / 指定歌词
  3. **标注来源**：UI 上标明歌词来自外部源（与 `LyricSheet.source` 字段对接）
- 匹配算法要点：歌名规范化 → 艺术家规范化 → 时长容差 ±3s → 相似度打分 → **超过阈值才自动采用**，否则交给用户确认

### 3.5 优先级建议

| 优先级 | 事项 | 理由 |
| --- | --- | --- |
| **P1（一期）** | 多版本择优（T1 > T2 > T3）+ 本地歌词缓存 + 无歌词态文案 | 服务端本来就有逐字歌词，只是没被选中 —— **修 bug 级收益，成本极低** |
| P2 | UI 提供「歌词版本切换」（多版本并存时让用户选）+ 逐字/整行标记 | 让 `alternates` 有出口 |
| P3（二期） | 外部歌词源匹配 + 纠错入口 | 有版权与稳定性风险，且依赖匹配算法成熟度 |

1. **歌词择优 + 本地缓存**（P1，独立、风险最低、收益立竿见影，可先做）
