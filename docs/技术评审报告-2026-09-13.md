## 一、结论摘要

这个仓库的**局部工程质量明显高于同类个人项目**：核心模块有长篇「为什么这么写」的注释、
纯逻辑抽成 policy 模块、架构契约测试兜底、转码方案做过 8 种格式的实测评估。
这些问题意识是真实的资产。

**但它的质量保障几乎全部是「约定」，不是「机制」。**

所有硬规则都以散文形式存在（交接文档、`MEMORY.md`、代码注释），没有任何一条被自动化执行。
散文规则会衰减，而且衰减是**静默**的 —— 不报错、不崩溃，只是悄悄不再生效。
本次评审抓到的两个最重要问题，都是这个模式的产物：

| 问题 | 性质 |
| --- | --- |
| `setup.ts` 的「热重载容错」分支匹配串少了 `been`，**从来没命中过** | 注释说它工作正常，实际恒为 false |
| `haptics.ts` 写了「触感统一走这里」，实际 **9 个文件 19 处绕过** | 规则写在注释里，已经漂移 |

一句话概括改进方向：**把能机械判定的规则变成检查，把最高风险的代码从「文本断言」升级成「行为测试」。**

本次已落地 5 项改动（含 1 个真实 bug 修复），见第四节。

## 三、发现分级

### 🔴 P0-1 `setup.ts` 热重载容错分支恒不生效 —— **真实 bug，已修复**

**位置**：`apps/mobile/src/player/setup.ts:48`

```ts
// 修复前
const message = error instanceof Error ? error.message : String(error)
if (!message.includes('already initialized')) throw error   // ← 恒为 true，永远抛
```

**为什么恒不生效**：RNTP 三端抛出的原文是

```
The player has already been initialized via setupPlayer.
```

中间多一个 **`been`**，所以 `includes('already initialized')` 恒为 `false`。
（已核对依赖源码：iOS `ios/RNTrackPlayer/RNTrackPlayer.swift:165`、
Android `android/src/main/java/com/doublesymmetry/trackplayer/module/MusicModule.kt:167`、
web `web/TrackPlayer/Player.ts:42`，错误码均为 `player_already_initialized`。）

**影响**：热重载 / Fast Refresh 后原生播放器已经初始化，`setupPlayer` 必然抛这个错。
本该被吞掉并继续走 `applyPlayerOptions()`，实际直接往上抛 → `ensurePlayer()` reject →
**播放/暂停/上一首/点歌全部没反应，且每次重试都必然失败**。这正是交接文档里
「整个播放器永久不可用」那个失效模式，只是触发条件被低估了。

**已修复**：改成「错误码优先 + 文案放宽」（同时出现 `already` 与 `initialized` 即认定），
并在注释里写清了这次近似匹配的教训。

**已验证修复有效**：新增 15 条行为测试，其中「已初始化」相关用例在修复前**失败**、
修复后通过 —— 测试确实有牙齿，不是摆设。

### 🔴 P0-2 播放器核心没有行为测试，只有「源码文本断言」

**证据**：`apps/mobile/test/unit` 下 43 个测试文件，**没有任何一个 import 过 `@/player/controller` 或 `@/player/bridge`**。

对这两个文件的「测试」长这样（`player-queue-interaction.test.ts:92`）：

```ts
const controllerSource = readSource('player/controller.ts')
expect(controllerSource).toContain('someExpectedCode')
```

即**断言源码里有没有某段字符串**。这类断言的问题：

- 改个变量名、换个等价写法，测试就挂 —— 但功能其实没坏（假失败）；
- 反过来，真正改坏逻辑只要字符串还在，测试就绿 —— 而它**抓不到任何运行时问题**（假通过）；
- 交接文档自己也承认：**「脆性测试改造机制建立（3/16 文件已迁移）」—— 还有 13 个文件没迁**。

**风险集中在哪**：`controller.ts`(957 行) + `bridge.tsx`(305 行) + `audio-cache.ts`(315 行)
+ `transcode-cache.ts`(238 行) ≈ **1800 行最高风险代码，零行为覆盖**。
而 `MEMORY.md` 记录的 5 条 RNTP 运行时坑（错误字段两端不一致、队列看门狗、
`ensurePlayer` 不能缓存 rejected promise……）**全部落在这片区域**。

这不是「测试不够多」的问题 —— 378 个测试并不少；是**测试放错了地方**：
大量文本断言消耗了维护成本，却没有覆盖真正会崩的地方。

**本次已给出可复制的做法**：新增的 `player-setup-resilience.test.ts` 演示了怎么给
「依赖原生模块的代码」写行为测试（`vi.mock` 原生模块 + `vi.resetModules()` 拿全新模块实例）。
这个模式可以直接套到 `controller.ts` / `bridge.tsx` 上。

### 🟡 P1-1 `apps/mobile` 的类型严格度低于 `packages`（差 116 个错误）

**证据**：`apps/mobile/tsconfig.json` 只 `extends: "expo/tsconfig.base"` 并设 `strict: true`，
**没有** `extends` 仓库根的 `tsconfig.base.json`。于是三个包有的开关它没有：

| 开关 | 三个包 | apps/mobile |
| --- | --- | --- |
| `strict` | ✅ | ✅ |
| `noUncheckedIndexedAccess` | ✅ | ❌ |
| `noImplicitOverride` | ✅ | ❌ |
| `verbatimModuleSyntax` | ✅ | ❌ |
| `isolatedModules` | ✅ | ❌ |

**代价量化**（探针实测）：把这三个包同款开关加到 `apps/mobile` 上，立刻暴露 **116 个错误**：

| 错误码 | 数量 | 含义 |
| --- | --- | --- |
| TS6133 | 39 | 未使用的变量 / 参数 |
| TS2375 + TS2379 | 57 | `exactOptionalPropertyTypes` 相关的可选属性问题 |
| TS2532 + TS18048 | 12 | 可能为 `undefined` 的索引访问 |
| TS2345 + TS2321 + TS6196 | 8 | 其它类型不匹配 |

**这是「口径不一致」而不是「代码差」**：约 2 万行、代码量最大的 `apps/mobile` 用的是最松的标准，
而三个小包用最严的。建议按**棘轮**推进：先加 `noUncheckedIndexedAccess`（12 处，收益最高、成本最低），
再逐步上 `exactOptionalPropertyTypes`。

### 🟡 P1-2 散文规则已经漂移：触感收口被 9 个文件绕过

`src/lib/haptics.ts` 的注释写得非常清楚：

> 之前每个调用点各自手写 `Haptics.impactAsync(...)`，结果必然漂移……
> 这类问题不该靠 review 一个个抓，而是让「加触感」只有一个地方可写。

**实测：9 个文件、19 处仍然直接调用 `Haptics.*`**（`confirm-modal` 4 处、`prompt-modal` 4 处、
`player-queue` 2 处、`appearance-settings` 2 处、`cache-settings` 2 处、`lyric-view` 2 处、
`option-picker-modal` 1 处、`progress-bar` 1 处、`HeroStationCard` 1 处）。

**根因不是「有人不守规矩」，而是抽象太薄**：`haptics.ts` 只导出了两个函数：

```ts
export function tap(): void     // Light impact
export function select(): void  // selection
```

而实际用到的语义有 **Light / Medium / Heavy impact + Warning / Error notification**
共 5 类。**模块表达不了真实需求，调用点就只能绕过去** —— 光靠 review 喊「用 tap()」是治不好的。

**正确修法**：先把 `haptics.ts` 的词汇补齐（例如
`tap()` / `tapStrong()` / `select()` / `warn()` / `fail()`，内部映射到具体 `ImpactFeedbackStyle`），
再迁移 19 处调用点，最后靠守卫锁死。本次已把这条规则接入守卫（存量记账、新增即失败）。

### 🟡 P1-3 根校验命令在本地跑不了 → 已修

**证据**：根 `package.json` 原本是 `"typecheck": "pnpm -r --if-present typecheck"`。
本机 `pnpm -r` 会触发依赖状态检查报 `EEXIST symlink`，于是**开发者被迫手打 4 段命令**。

**校验一旦需要 4 段手打命令，就必然被跳过** —— 这是流程问题，不是纪律问题。

**已修**：新增 `scripts/verify.mjs`，直接调用各包自带的 `tsc` / `vitest`，绕开 pnpm：

```bash
node scripts/verify.mjs                 # 守卫 + 4 包类型检查 + 4 包单测，共 9 项
node scripts/verify.mjs --only typecheck
```

实测 **9 项全过，总耗时约 40 秒**。本地和 CI 现在跑的是同一条命令。

**棘轮（ratchet）是什么意思**：存量债务记在基线文件里，**不阻塞任何人**；
但**新增一处就失败**，并指出具体文件行号。修掉债务后守卫会提示你下调基线。
这样规则可以立刻落地，而不是「等还完债再开」。

守卫本身也做了**牙齿验证**：临时造一个含 `console.log` + 绕过 haptics + 新增 `as never`
的文件，守卫正确报出 3 类违规并以退出码 1 失败。

> 顺带一个有意思的自证：守卫最初把 `@ts-ignore` 规则写成扫「去注释后的源码」，
> 而 `@ts-ignore` 本身就在注释里 —— 于是这条规则**永远不可能命中**。
> 这正是 P0-1 的同一种失效模式，只不过这次发生在检查器自己身上。
> 是「牙齿验证」把它揪出来的。**所以：每加一条检查，都要先证明它会失败。**

## 六、团队能力提升：三条可复用的做法

这部分是给「怎么让团队整体变强」的，比修单个 bug 更重要。

### 1. 规则要写进代码，不要写在文档里

本次最强的两个证据（P0-1、P1-2）都是同一个原因：**规则写对了，但没人执行**。
判据很简单：**如果一条规则只能靠人记得，它迟早会失效。**

落地方式就是本仓库已有的那套思路的延伸 —— 你们已经在做
`capability-consistency.test.ts` 这种「契约测试」了，方向完全正确，
只是覆盖面还停在「能力声明四层一致」，没扩展到编码规范。守卫脚本就是补上这一块。

### 2. 每写一条检查，先证明它会失败

守卫自己踩的 `@ts-ignore` 坑就是最好的例子：
一条「永远为真」的检查**比没有检查更危险**，因为它会让人以为这件事已经被守住了。

做法：加完检查，立刻造一个违规样本跑一遍，确认它以非零退出码失败。
本次守卫的 6 条规则全部做过这一步。

### 3. 测试要断言行为，不要断言源码文本

`readSource(...).toContain('...')` 这种断言**两头都不可靠**：
换个等价写法就假失败，逻辑改坏却可能假通过。

判断标准：**把被测代码改坏，测试会不会失败？**
- `player-setup-resilience.test.ts` 做过这个验证：把 `setup.ts` 改回 bug 版本，
  2 条用例立刻失败 —— 这才叫测试。
- 源码文本断言做不到这一点。

文本断言**只在一个场景下合理**：断言「某个写法被彻底移除」这类
「禁止出现 X」的约束（`hasNoCode`），此时它和 lint 是一回事，
**更好的做法是把它交给守卫/lint，而不是测试**。
