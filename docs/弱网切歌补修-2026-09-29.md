# 弱网加载中切歌：补修与复验

日期：2026-09-29。用户反馈：歌曲加载时点击上一首、下一首，界面仍卡在原歌曲。

本次由主代理修改生产代码、复审并决定验收；GPT-6-luna 负责独立复现、回归用例和边界复查。尚未确认用户设备安装的是哪次构建；以下是当前源码中已复现的问题，不把模拟测试结果当成设备日志。

## 已确认的原因

1. 上一首仍排在旧播放任务的串行队列后面。旧加载或原生 `play()` 不结束时，新操作不能开始。
2. 普通下一首仅依据 JS `isLoadingAudio` 决定是否撤销旧意图，而原生缓冲状态可能独立存在；它还在原生提交队列中等待 `play()`，导致第二次切换继续排队。
3. 列表和单曲的歌名、封面在资源准备及原生提交后才更新。即使开始了新请求，用户看到的仍是旧歌曲。
4. 连续点击时没有保存未提交的选择位置：下一首后立即上一首、上一首后下一首、连续上一首，都可能从旧队列位置计算错误。

这是上一轮 F01/F02 修复和回归覆盖中的遗漏。本记录补充《本轮修复与验收记录》，不将此前通过的测试解释为全场景通过。

## 修复后的行为

- 点击时同步发布 `pendingCurrent`，歌名、封面立即跟随选中目标；加载期间进度显示从零开始，播放按钮保持加载态。
- 加载目标与已提交的原生队列分开。连续点击使用暂存导航位置计算，只有最新播放意图有权提交。
- 下一首按曲目 occurrence id 查找实际原生下标，避免异步移除曲目后切错歌；原生提交队列不再等待网络缓冲中的 `play()`。
- 原生 skip 成功后立即同步当前项和历史，不再等待缓冲结束或迟到的激活事件；桥接层避免重复提交历史。
- 上一首连续选择可一次恢复对应历史范围；取消后按本次唯一 id 清理可能已插入的原生项。
- 新目标准备期间过滤不匹配的原生换曲事件和无法归属的新旧错误事件，避免把旧歌曲的事件套到新目标上。
- 单曲播放没有下一首时保持当前请求，不借用旧队列的待播歌曲。操作失败通过界面提示，不静默吞掉。
- 列表分页来源在成功提交队列后登记，避免旧 `play()` 等待期间被新切歌撤销后丢失续页状态。

立即切换指立即改变选中歌曲并开始处理新意图；音频仍需网络缓冲。无法从 JS 撤销已经发出的原生调用；真正的原生回调挂起仍受原生提交队列的 10 秒超时保护。本次没有宣称原生执行、出声或弱网缓冲具备固定毫秒延迟保证。
