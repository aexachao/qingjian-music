# 构建与 CI（在 GitHub 上构建，本机不装环境）

> 日期：2026-09-13
> 背景：本机没有 JDK / Android SDK / Xcode，`gradlew assembleDebug` 与真机验证做不了。
> 方案：把原生构建搬到 GitHub Actions，本机只负责写代码。

---

## 一、怎么触发

| 方式 | 操作 | 用途 |
| --- | --- | --- |
| 手动 | Actions → **Build** → Run workflow | 随时出一版包 |
| 打 tag | `git tag v0.1.0 && git push origin v0.1.0` | 发版；APK 会自动挂到 GitHub Release |
| 日常 | 推送到 `master` | 只跑 **CI**（守卫 / 类型 / 单测），不出包 |

两个工作流分工：

| 文件 | 触发 | 内容 |
| --- | --- | --- |
| `.github/workflows/ci.yml` | push / PR / 手动 | 架构守卫、类型检查、单测；（可选）契约测试 |
| `.github/workflows/build.yml` | 手动 / tag | 校验 → JS 打包检查 → Android APK → iOS 构建 |

## 二、产物说明

### `android-debug-apk` —— **可以直接装到真机**

```
app-debug.apk
```

- **debug 包**，用 Gradle 自动生成的 debug keystore 签名，不需要任何 Secrets；
- 直接 `adb install app-debug.apk` 或传到手机点击安装即可；
- 这正是交接文档 P0 里「Android 真机验证」需要的东西 ——
  **现在可以在 GitHub 上出包，再用真机验证，不需要在本机装 Android 环境。**

> 为什么先出 debug 而不是 release：release 需要你自己的签名密钥（keystore），
> 且密钥不能进仓库。debug 包已经能完成真机功能验证，这是当前最缺的一环。
> 需要 release 包时的配置方法见第四节。

### `ios-simulator-app` —— **只验证能编译，不能装真机**

```
app-ios-simulator.zip   （内含 app.app）
```

- 用 `CODE_SIGNING_ALLOWED=NO` 构建，**未签名**，只能跑模拟器；
- 价值在于：它在 macOS runner 上真的跑了 `expo prebuild` + `pod install` + Xcode 编译 +
  **Release 配置下的 JS 打包**，能验证「原生工程能不能编过」——
  这是本机完全做不到的那部分；
- 想装真机 / 出 IPA 需要签名凭据，见第五节。

### JS 打包检查（不出产物，但很快）

`bundle` job 会分别对 iOS / Android 跑 `expo export`，约 2 分钟。
它能提前抓到「模块解析不到 / 平台后缀缺失」这类问题，
不用等 20 分钟的原生构建失败才发现。

## 三、工作流里几个「不这么写就会坏」的点

这些都是踩过的坑，改工作流时不要动：

1. **`expo prebuild --platform ios` 不能加 `--no-install`。**
   它会清空并重写整个 `ios/` 目录却跳过 `pod install`，
   导致 `.xcworkspace` 不存在，`xcodebuild` 直接报 workspace 找不到。
   （Android 侧加 `--no-install` 没问题，因为没有 pod 这一步。）

2. **`android/` 和 `ios/` 都被 `.gitignore` 排除**，CI 上必须现生成，
   所以工作流里一定有 prebuild 步骤，不能假设原生目录存在。

3. **`plugins/` 和 `modules/` 必须提交。**
   它们曾被漏掉（`with-app-icons.js`、`with-android-cleartext.js`、
   `modules/app-icon/`、`modules/system-volume/android/`），
   漏了会导致 prebuild 失败或构建出的 App 缺功能。
   本次已一并提交。

4. **构建前先跑 `verify` job。** 坏提交不给包。

5. **xcodebuild 日志重定向到文件，失败时只打错误摘要 + 末尾片段。**
   Xcode 日志动辄上万行，直接打到 CI 日志里会把真正的错误冲掉。

## 四、Android release 包（需要时再配）

release 包需要一个签名密钥。**密钥不能进仓库**，走 Secrets：

1. 本地生成（只需一次）：
   ```bash
   keytool -genkeypair -v -storetype PKCS12 \
     -keystore release.keystore -alias qingjian \
     -keyalg RSA -keysize 2048 -validity 10000
   base64 -i release.keystore | pbcopy     # macOS，复制到剪贴板
   ```
2. 仓库 Settings → Secrets and variables → Actions 添加：
   | Secret | 内容 |
   | --- | --- |
   | `ANDROID_KEYSTORE_BASE64` | 上一步的 base64 |
   | `ANDROID_KEYSTORE_PASSWORD` | keystore 密码 |
   | `ANDROID_KEY_ALIAS` | `qingjian` |
   | `ANDROID_KEY_PASSWORD` | key 密码 |
3. 加一个 config plugin 把签名配置写进 `android/app/build.gradle`
   （参考 `plugins/with-ios-signing.js` 的写法），再在 `build.yml` 里
   加 `assembleRelease` 步骤并读这些 Secrets。

> **注意**：`expo prebuild` 会重写 `android/`，所以签名配置**必须走 config plugin**，
> 直接改 `android/app/build.gradle` 会在下次 prebuild 时丢失。
> 这也符合项目既有约定：原生配置一律走 plugin，且改完要去产物里 grep 验证。

## 五、iOS 真机 / IPA（需要时再配）

iOS 签名是唯一比 Android 麻烦的地方。两条路：

### 路线 A：App Store Connect API Key（推荐，免维护描述文件）

1. App Store Connect → Users and Access → Integrations → 生成 API Key（角色 App Manager），
   下载 `.p8`（**只能下载一次**）；
2. 记下 Key ID 和 Issuer ID；
3. Secrets：
   | Secret | 内容 |
   | --- | --- |
   | `ASC_KEY_ID` | Key ID |
   | `ASC_ISSUER_ID` | Issuer ID |
   | `ASC_KEY_P8_BASE64` | `.p8` 文件的 base64 |
4. 构建时改用：
   ```bash
   xcodebuild -workspace ios/app.xcworkspace -scheme app \
     -configuration Release -destination 'generic/platform=iOS' \
     -allowProvisioningUpdates \
     -authenticationKeyPath "$RUNNER_TEMP/AuthKey.p8" \
     -authenticationKeyID "$ASC_KEY_ID" \
     -authenticationKeyIssuerID "$ASC_ISSUER_ID" \
     archive -archivePath "$RUNNER_TEMP/app.xcarchive"
   ```
   再 `xcodebuild -exportArchive` 出 IPA。
   `plugins/with-ios-signing.js` 已经把 `DEVELOPMENT_TEAM` 设成 `4NJM425J3B`，
   `-allowProvisioningUpdates` 会用它自动拉描述文件。

### 路线 B：手动证书 + 描述文件

Secrets：`BUILD_CERTIFICATE_BASE64`、`P12_PASSWORD`、`BUILD_PROVISION_PROFILE_BASE64`、
`KEYCHAIN_PASSWORD`，在 runner 上临时建 keychain 导入证书。
步骤繁琐、描述文件会过期，只在路线 A 不可用时用。

## 六、替代方案：EAS Build（`eas.json` 已经就绪）

如果连 GitHub Actions 的签名配置也不想折腾，可以直接用 Expo 官方的云构建 ——
它**自带 iOS 签名托管**，这是它相对自建 CI 的最大优势。

```bash
# 本机只需要 npx，不需要 Xcode / JDK
npx eas-cli build --platform all --profile preview
```

或者在 GitHub Actions 里触发（加 `EXPO_TOKEN` secret）：

```yaml
      - name: EAS Build
        working-directory: apps/mobile
        run: npx eas-cli@latest build --platform all --profile preview --non-interactive
        env:
          EXPO_TOKEN: ${{ secrets.EXPO_TOKEN }}
```

| | GitHub Actions（已配置） | EAS Build |
| --- | --- | --- |
| 费用 | 免费额度（macOS runner 按 10 倍分钟计） | 免费额度有限，超出按量付费 |
| Android APK | ✅ 已可用 | ✅ |
| iOS 真机 / IPA | 需自行配签名 | ✅ **托管签名**，最省事 |
| 可控性 | 高（能加任意步骤） | 中 |
| 首次配置 | 已完成 | 需要 Expo 账号 + `EXPO_TOKEN` |

**建议**：Android 用现在这套（已可用）；等到要出 iOS 真机包时，
再决定是配路线 A 还是切 EAS。

## 七、首次跑之前值得知道的

- **`pnpm install --frozen-lockfile` 会失败**，如果 `pnpm-lock.yaml` 与
  `package.json` 不同步。改依赖后务必本地跑一次 `pnpm install` 并一起提交。
- **macOS runner 按 10 倍计费**。iOS job 约 20-30 分钟 ≈ 200-300 分钟额度。
  日常推送只跑 `ci.yml`（ubuntu），不出包就不会消耗。
- **Gradle 缓存**已按 `pnpm-lock.yaml` 的哈希做 key，首次构建会慢（要下依赖），
  之后会快不少。
- **RNTP 的 patch 通过 `pnpm-workspace.yaml` 的 `patchedDependencies` 生效**，
  `pnpm install` 时自动打上。如果发现播放器行为不对，先去
  `node_modules/react-native-track-player` 确认 patch 有没有应用。
