## 1. [P1] iOS 下载启动后删除分片目录，文件无法落盘

位置：[AudioDownloaderSession.swift:108](/Users/chrisli/Documents/dev/qingjian-music/apps/mobile/modules/audio-downloader/ios/AudioDownloaderSession.swift:108)、[同文件:213](/Users/chrisli/Documents/dev/qingjian-music/apps/mobile/modules/audio-downloader/ios/AudioDownloaderSession.swift:213)、[同文件:302](/Users/chrisli/Documents/dev/qingjian-music/apps/mobile/modules/audio-downloader/ios/AudioDownloaderSession.swift:302)。

`start` 先保存新 job、创建 `partsDirectory`，随后 `cancelTasks(removeParts: true)` 从 `jobs[jobId]` 取得的正是新 job，并删除该目录。此后没有重建目录，`didFinishDownloadingTo` 直接 move 到不存在的父目录，错误被吞掉。普通首次下载也会遇到，不需要弱网。作业可能一直没有完成结果；启动对账只拼已有完整分片，也没有实现注释声称的重新下载。

复现：复制当前 Swift 核心到 macOS Foundation 夹具，仅替换后台 session 为 ephemeral、状态目录为临时目录及后台完成处理器。输出 `startAccepted=true partsDirectoryExists=false`、`partSaved=false`。这验证文件操作路径，未替代 iPhone 后台生命周期实测。

建议：先取消旧任务并清理旧目录，再登记新任务并创建目录；文件搬运失败必须发出失败事件。

## 2. [P1] 重登录接口返回 401 时，鉴权链路永久等待

位置：[client.ts:89](/Users/chrisli/Documents/dev/qingjian-music/packages/provider-fnos/src/client.ts:89)、[client.ts:99](/Users/chrisli/Documents/dev/qingjian-music/packages/provider-fnos/src/client.ts:99)、[provider.ts:190](/Users/chrisli/Documents/dev/qingjian-music/packages/provider-fnos/src/provider.ts:190)。

业务请求 401 → `refreshToken` → `silentRelogin` → 同一个 client 发登录请求。若登录接口本身也返回 HTTP 401 或被映射为 unauthorized，登录请求再次进入 `refreshToken`，返回正在等待该登录请求的 `refreshing` Promise，形成循环等待。注释说排除了登录接口，实际代码未判断 path。

复现：全部请求返回 HTTP 401，真实 FnosProvider 发出两次 HTTP 请求后不再推进；虚拟时间推进 60 秒，调用仍未成功或失败。HTTP 已经返回，HTTP 超时无法解除这个 Promise 循环。同一实例后续需要重登录的请求也会被卡住。

建议：登录、登出使用明确禁用 reauth 的调用路径；刷新失败要清理状态并向上层返回确定错误。覆盖登录失败、代理 401、并发刷新失败。

## 3. [P1] 播放超时只结束外层 Promise，旧操作会恢复并覆盖新点播

位置：[mutation-queue.ts:41](/Users/chrisli/Documents/dev/qingjian-music/apps/mobile/src/player/mutation-queue.ts:41)、[mutation-queue.ts:60](/Users/chrisli/Documents/dev/qingjian-music/apps/mobile/src/player/mutation-queue.ts:60)、[controller.ts:283](/Users/chrisli/Documents/dev/qingjian-music/apps/mobile/src/player/controller.ts:283)。

看门狗 reject 后放行后续操作，但没有取消旧任务或禁止其后续写入。`playSingleTrackMutation` / `playTrackListMutation` 在耗时请求后仍 reset/add/setQueue/play，没有检查 generation。慢网络、刷新 token 加转码的组合延迟，或原生回调延迟都会扩大风险。

复现：A 的 stream 挂起，30 秒超时；随后 B 正常点播；A 再返回，队列从 B 被改回 A。A 挂起期间，外层虽然已经超时，`isLoadingAudio` 仍为 true，因为内层 finally 尚未执行。另一个设计问题是超时从提交任务开始计时，排队等待也会消耗任务预算。

建议：把 generation/cancellation 检查贯穿耗时步骤和每次播放器/store 写入；超时必须使旧操作失效；看门狗从实际开始执行计时，并由能结束的外层维护 loading 状态。

## 4. [P2] 旧列表的慢分页响应污染新播放列表，并跳过新列表的一页

位置：[controller.ts:205](/Users/chrisli/Documents/dev/qingjian-music/apps/mobile/src/player/controller.ts:205)。

`fillFromListFeed` await 之前读取旧 listFeed，返回后却直接修改当前全局 listFeed，并向当前队列追加旧页。没有保存并核对 feed 实例或 generation。

复现：A 的第 2 页挂起 → 改播 B → A 响应回来，队列变成 `[B, A第2页]`；B 的下一次拉页直接请求第 3 页，第 2 页被跳过。

建议：捕获 feed 身份及播放代次；响应返回、实际入队时都验证归属。旧任务 finally 也不能清除新任务的 filling 标志。

## 5. [P2] 后台下载完成后重启，无法恢复“已下载”登记

位置：[downloads.ts:114](/Users/chrisli/Documents/dev/qingjian-music/apps/mobile/src/player/downloads.ts:114)、[downloads.ts:589](/Users/chrisli/Documents/dev/qingjian-music/apps/mobile/src/player/downloads.ts:589)。

恢复登记依赖 `pendingSettlements`，它只是内存 Map。进程重启后丢失 title、track、serverId 等元数据；原生 pendingJobs 虽能帮助拼文件，但完成事件的 `settle` 找不到 pending 元数据就返回。所谓磁盘对账也只遍历这个空 Map，没有扫描并恢复完整元数据。iOS 完成后还会移除 native job。Android 也使用同一 JS 登记逻辑。

复现：发起原生下载 → 重置 JS 内存 → 原生报告完整作业并发送完成事件 → `listDownloads()` 仍为空。

建议：提交原生作业之前持久化待完成元数据；完成登记成功之后再移除 journal。覆盖重启、完成事件丢失、索引写盘失败以及磁盘空间不足。

## 6. [P2] 转码曲目的本地缓存/下载优先级未贯通播放路径

位置：[controller.ts:146](/Users/chrisli/Documents/dev/qingjian-music/apps/mobile/src/player/controller.ts:146)、[controller.ts:858](/Users/chrisli/Documents/dev/qingjian-music/apps/mobile/src/player/controller.ts:858)、[bridge.tsx:209](/Users/chrisli/Documents/dev/qingjian-music/apps/mobile/src/player/bridge.tsx:209)。

有两个入口不一致：首次点播的 `toRntpTrack` 在需要转码时直接联网，不查询 `cachedTranscodeUri`；而换歌回调的 `ensureTranscodeForIndexMutation` 只检查转码缓存，不检查用户下载文件。于是本地已有转码缓存，断网点播仍会失败；已经下载的 DSF 等曲目起播后又可能被事件回调换成在线 HLS。

复现一：已有 `file:///cached-transcoded.mp4`，stream 抛 offline，首次点播仍失败且队列为空。复现二：downloadedUri 有本地 MP4，调用事件使用的 ensure 方法仍请求 stream，并 load 在线地址。第二种情况下若网络立即失败，原本加载的本地文件未必停止；确定缺陷是多余联网及成功后替换本地源，不夸大为每次离线必然失败。

建议：统一媒体解析顺序：用户下载 → 已验证的转码缓存/原文件缓存 → 在线流；桥接回调识别当前本地来源，不重复换流。

## 7. [P2] iOS 下载把 HTTP 错误响应当成音频文件

位置：[AudioDownloaderSession.swift:295](/Users/chrisli/Documents/dev/qingjian-music/apps/mobile/modules/audio-downloader/ios/AudioDownloaderSession.swift:295)、[同文件:318](/Users/chrisli/Documents/dev/qingjian-music/apps/mobile/modules/audio-downloader/ios/AudioDownloaderSession.swift:318)。

建议：仅接受预期成功状态；非成功响应清理临时文件并上报失败，针对 transient 状态采用有界重试；必要时校验长度与媒体类型。

## 8. [P2] 已下载列表跨服务器混用，播放时把所有歌曲改成当前服务器身份

位置：[downloaded.tsx:40](/Users/chrisli/Documents/dev/qingjian-music/apps/mobile/src/screens/downloaded.tsx:40)、[downloaded.tsx:51](/Users/chrisli/Documents/dev/qingjian-music/apps/mobile/src/screens/downloaded.tsx:51)、[downloaded.tsx:60](/Users/chrisli/Documents/dev/qingjian-music/apps/mobile/src/screens/downloaded.tsx:60)。

证据级别：明确静态代码路径，未做双服务器真机复现。

建议：按 serverId 过滤可播集合，或保留每一条下载的真实服务器归属并设计独立离线播放入口。

## 补充审计：加载时下一首无反应、登出等待

用户补充的两个现象均已找到可复现的代码路径。以下按实际交互说明，与问题 3 的异步失效/队列阻塞存在共同根因，不简单累加前面的缺陷数量。本轮仍未修改业务代码。

### A. 歌曲加载时点击下一首无反应

[下一首入口 controller.ts:550](/Users/chrisli/Documents/dev/qingjian-music/apps/mobile/src/player/controller.ts:550)；[列表起播 controller.ts:242](/Users/chrisli/Documents/dev/qingjian-music/apps/mobile/src/player/controller.ts:242)；[转码操作入队 controller.ts:942](/Users/chrisli/Documents/dev/qingjian-music/apps/mobile/src/player/controller.ts:942)。

两处按钮（mini-player 与 player-deck）均未因 loading 禁用下一首，点击会进入 skipToNextSafe。问题出在后续状态与请求时序：

1. **新列表尚未建立，点击被丢弃。** playTrackListMutation 等待所有播放地址解析后才 setQueue。当前列表 [A,B] 正在加载时，skipToNextSafe 读取的仍是旧 queue；如果旧 queue 只有一首，就认为“已经是最后一首”直接 return，不记录下一首意图。复现中 A 的流请求延迟，点击下一首没有调用原生 skip，A 加载完成后仍从 A 开始。
2. **下一首的转码请求等旧请求结束。** 已有队列中，skipToNextSafe 本身没有加入 mutation 队列，但播放桥接为新歌曲调用的 ensureTranscodeForIndex 要排队；旧 A 的转码请求还占着队列，B 的转码初始化无法开始。复现中模拟原生切歌事件已把当前曲目切到 B，再推进 5 秒，provider 仍只收到 A 的请求；A 返回后 B 才开始请求。首次转码请求超时配置为 20 秒，鉴权刷新等组合步骤还会增加等待。

影响：触感/点击可能已触发，但播放没有及时切换；也不能靠多点几次可靠地跳过卡住的歌曲。原生缓冲慢且不涉及这两条 JS 路径的情况，仍需真机验证。

修复方向：区分“用户期望播放的歌曲”和“已经加载到原生的歌曲”；下一首立即推进播放意图、使旧加载任务失效并尽可能取消网络请求。旧网络等待不应占着唯一的队列变更通道，真正的原生队列提交仍须受控串行。新意图已经变化时，旧任务不得再 load/play 或覆盖 loading 状态。

### B. 点击登出必须等待网络和播放器清理

[server-session.tsx:192](/Users/chrisli/Documents/dev/qingjian-music/apps/mobile/src/lib/server-session.tsx:192)；[session-state.ts:20](/Users/chrisli/Documents/dev/qingjian-music/apps/mobile/src/lib/session-state.ts:20)；[provider.ts:227](/Users/chrisli/Documents/dev/qingjian-music/packages/provider-fnos/src/provider.ts:227)；[controller.ts:654](/Users/chrisli/Documents/dev/qingjian-music/apps/mobile/src/player/controller.ts:654)；[settings.tsx:107](/Users/chrisli/Documents/dev/qingjian-music/apps/mobile/src/screens/settings.tsx:107)。

当前顺序：读取/保存账号历史 → await provider.logout → await clearQueue → 清查询缓存与凭证 → 发布 signedOut → 页面跳转。用户必须等前面步骤完成才能离开登录态。

已验证的等待来源：

- 服务端 logout 单次请求有 2 秒上限，但在本地退出之前 await，网络无响应时仍先等这 2 秒。
- logout 仍走 withReauth。若先返回 401，会触发默认 15 秒超时的密码登录请求，因而整体并非最多 2 秒。新增复现中 2 秒时仍未结束，约 15 秒后才结束；如果登录也返回 401，还会触发前述问题 2 的循环等待。
- clearQueue 排在播放 mutation 后面。新增复现使用真实 teardownSession 与 controller：旧 stream 悬挂 5 秒时，原生 reset、清凭证和发布 signedOut 均未执行。旧加载返回后退出才完成；看门狗默认 30 秒也不能保证旧任务随后不会恢复执行。
- 清队列还会依次等待预热会话 close 与当前转码会话 close。对应服务端 quit 单次请求为 3 秒上限，且也可能进入鉴权恢复，进一步增加退出等待。

修复方向：登出先使播放、续页、重登录等在途操作失效；本地停止播放、清除可见状态与持久凭证需要明确且有界的完成路径。服务端 logout/quit 作为独立有界清理，不阻塞本地退出，也不得在退出过程中触发静默重登录。不能仅提前跳登录页而放任旧播放任务和凭证回写继续执行。
