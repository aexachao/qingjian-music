## 一、歌单：写接口实测

### ✅ 可用（已回读验证）

| 接口 | 实测结果 |
| --- | --- |
| `POST /playlist/create {name}` | `code:0`，`data` 是**完整对象**：`{guid, name, coverId:null, createdAt, updatedAt}` |
| `coverId` 省略 | ✅ 可省略 |
| `coverId: ""` | ✅ 接受，回写为 `null` |
| 重名创建 | `code:160001`，`msg:"playlist name already exists"` |
| `POST /playlist/edit {guid, name}` | `code:0`；**改名后回读 `playlist/list` 确认已持久化** ✅ |
| `POST /playlist/delete {guid}` | `code:0`；回读列表确认已删除 ✅ |
| `GET /playlist/list` | `{list:[…]}`；条目字段仅 `{guid, name, coverId, createdAt, updatedAt}`，**不含 `trackCount`** |
| `member` 角色权限 | ✅ 可创建 / 改名 / 删除歌单 |

### ❌ 不可用

| 接口 | 实测结果 |
| --- | --- |
| `POST /playlist/add-track {guid, trackGUIDs:[…]}` | 返回 `code:0`，但**完全不生效**：连续 3 次重试 + 每次等 2 秒后，`batch-detail` 仍为 `{list:[]}`、`detail` 仍 100002 |
| `GET /playlist/detail?guid=` | **`100002 invalid arguments`**。已穷举参数名 `guid` / `playlistGUID` / `playlistGuid` / `playlistId` / `id`，并试过 `POST`（POST 落到 SPA HTML），**全部失败** |
| `GET /track/playlist-detail/list?playlistGUID=&page=&size=&sort=` | **`100002`**。带 `sort=trackAddedAt,desc` 与不带都失败；**对「真实 guid」与「乱写的 guid」返回完全一样**，说明问题不在 guid |
| `GET /playlist/batch-detail?guids=` | `code:0`，但 `list` 恒为**空**（对真实 guid 与乱写 guid 都一样） |

### 关键对照（证明不是我们的用法问题）

| 观察 | 说明 |
| --- | --- |
| `playlist/edit` 改名**能持久化** | 「写入」这条链路是通的，不是通用写权限问题 |
| `purge-track-count?guid=<真实>` → `code:0 {total:0}`；`<乱写>` → `code:100002` | **服务器能区分 guid 真伪**，所以我们传的 guid 是有效的 |
| `playlist-detail/list` 对真假 guid 都 100002 | 该接口的问题与 guid 无关 |
| web 端调用点与我们的参数**完全一致**（`addTrack({guid, trackGUIDs})`、`detail({guid})`、`playlistDetailList({page, playlistGUID, size, sort})`） | **web 端自己也会遇到同样的失败** |

### 结论与两种可能

**结论**：歌单曲目功能在这台服务器（mediasrv 0.8.41）上不可用。

**两种可能的原因**（需 admin 账号才能进一步区分）：

1. **服务器版本未实现**：mediasrv 0.8.x，歌单曲目相关的读接口尚未可用（与「服务器上 0 个歌单」的现状吻合 —— 没人用起来过）
2. **member 权限不足**：歌单元数据属用户自有（可写），而歌单**内容**引用曲库资源，可能要求库写权限（admin）。服务端选择静默忽略而非返回 `100003`

### ⚠️ 附带发现：服务端对未知参数静默忽略

`POST /playlist/add-track {guid, guid2:[…]}`（故意写错参数名）也返回 `code:0`。

> **这意味着：参数名写错 → 「假成功」。App 绝不能凭 `code:0` 就报成功，必须回读校验。**

## 二、歌词：多版本假设被推翻

样本：1000 首曲目（5 页 × 200），逐首调 `/lyric/list`。

| 指标 | 实测值 |
| --- | --- |
| 有可用歌词 | **505 / 1000（50%）** |
| 每首歌的歌词条目数 | **恒为 1**（505 首全部只有 1 条，**多版本 0 例**） |
| 档位分布（按条目） | 整行 423、纯文本 82、**逐字 0** |
| `source` 字段 | **恒为 3**（全部 505 条），无法据此区分档位 |
| `preferred` | 恒存在，且恒指向唯一那条 → **不会出现「preferred 降级」** |
| 词级时间标签 | 方括号 `[mm:ss.xx]word` **0 命中**；尖括号 `<mm:ss.xx>word` **0 命中**（查了 221 条 LRC） |

### 对设计的三个修正

1. **「服务端给了多版本、只是没被选中」这个前提是错的。** 实测每首歌只有一条歌词，`preferred` 必然等于最优。所以 `mapLyricSheet` 的档位择优是**正确的防御性代码，但在当前数据上零效果** —— 它的价值只剩「服务器将来返回多版本时不会选错」+ `tier` 字段可供 UI 标注。
2. **逐字歌词在这套库里不存在。** 卡拉OK（逐字点亮）分支**永远不会触发**。想有逐字只能靠外部源，而主流外部源（LRCLIB）也只有整行 —— 所以「逐字优先」在当前数据下没有实际收益。
3. **真正的缺口是「50% 的曲目根本没有歌词」。** 外部歌词源的价值在于补这 50%，而不是「补逐字」。

### 仍待确认（本轮未验证）

- `/lyric/list` 的 `list` 是否**可能**返回多条（换个后端版本或某些特殊曲目）—— 本轮 1000 首零命中，但不足以断言永远为 1
- 其余约 40000 首里是否存在逐字歌词（抽样 1000 首，置信度有限）
