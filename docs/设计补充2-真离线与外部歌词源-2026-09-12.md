## 一、真离线

### 1.1 先回答你的疑问：缓存到底会不会被系统回收？

**会。而且「缓存大小设置」管不了这件事。**

`expo-file-system` 的类型定义里写得很直白（`node_modules/expo-file-system/build/Paths.d.ts`）：

| API | 官方说明（原文） |
| --- | --- |
| `Paths.cache` | *"a place to store files that **can be deleted by the system** when the device runs low on storage"* |
| `Paths.document` | *"a place to store files that are **safe from being deleted by the system**"* |

关键在于这是**两套互不相干的机制**：

| | 谁在删 | 何时删 | App 能否阻止 | 我们的「大小设置」管不管 |
| --- | --- | --- | --- | --- |
| 我们的缓存淘汰 | App 自己（LRU + 容量/首数上限） | 写入新文件时 | 能（就是它实现的） | ✅ 管的是这个 |
| 系统回收 | iOS / Android 系统 | 设备存储紧张 + App 不在前台 | **不能** | ❌ 完全管不到 |

所以现状是：`lib/cache-preferences.ts` 里的「上限 2GB / 1000 首」是**我们自己主动淘汰的上限**，它不构成任何「文件会一直在」的保证。系统该清还是会清，而且**不会通知 App**。

**为什么不能拿它当离线**：用户下载 50 首，某天磁盘紧张被系统清掉一部分，用户离线打开发现歌没了 —— 而且 App 自己也感知不到文件消失，无法给用户任何解释。这就是「信任崩塌」而不是「体验问题」。

### 1.2 真离线的定义

> 用户**主动下载** → 文件落在**系统不会回收**的目录 → **离线时可播** → 用户可**查看 / 删除 / 看到占用**。

四个要素缺一不可。特别注意最后一条：用户必须能管理它，否则「下载了但找不到、删不掉、不知道占了多少」比没有下载更糟。

### 1.3 存储分层：两套目录，一套读取优先级

| | 缓存层 | 离线层 |
| --- | --- | --- |
| 目录 | `Paths.cache/audio` | `Paths.document/downloads` |
| 谁删 | 系统 + App LRU | **仅用户** |
| 触发方式 | 播放时自动（边听边存） | 用户点「下载」 |
| 受容量/首数设置约束 | ✅ 受 | ❌ **不受** |
| 参与 LRU 淘汰 | ✅ 参与 | ❌ **不参与** |
| UI 承诺 | 不承诺（不展示为「已下载」） | **承诺离线可播** |
| 展示位置 | 设置 → 缓存（只给一个数字） | 「已下载」页（可管理列表） |

**读取优先级**（把现在的 `cachedAudioUri` 扩展为 `localAudioUri`）：

```
1. downloads 命中 → 用（离线保证）
2. cache 命中     → 用（加速）
3. 都没有         → 网络直推（并按设置决定是否写回 cache）
```

**一条硬规则**：离线层的文件**永远不参与缓存淘汰**，也不受缓存大小设置影响。否则用户会发现「我下载的歌被清了」—— 这是最容易犯的设计错误。

### 1.4 技术基础已就绪（好消息，不需要自己写原生下载模块）

`expo-file-system` SDK 57 的 `File.createDownloadTask` 能力比预期强得多（`NetworkTasks.d.ts`）：

| 能力 | API | 对应用户体验 |
| --- | --- | --- |
| 自定义请求头 | `options.headers` | ✅ **必须**：飞牛音频要带 `authorization` 头，否则 401 |
| 进度回调 | `options.onProgress` → `{ bytesWritten, totalBytes }` | 进度条 |
| 暂停 | `pause()` / `pauseAsync()` | 暂停按钮 |
| 续传 | `resumeAsync()` | 继续下载 |
| 取消 | `cancel()` | 取消按钮 |
| **跨进程持久化续传** | `savable()` / `DownloadTask.fromSavable(state, options)` | **App 被杀后重开仍能续** |

也就是说：进度、暂停、续传、取消、断点恢复全都有现成实现，我们只需要写队列与索引管理。

### 1.5 数据模型与索引

必须**自己维护索引**，不能靠扫目录：离线列表要显示标题 / 艺术家 / 封面 / 来源 / 大小 / 状态，而目录里只有文件名。

```ts
interface DownloadEntry {
  serverId: string
  trackId: string
  /** 文件名与最终落盘位置 */
  fileUri: string
  format?: string
  sizeBytes?: number
  /** 离线列表要展示的元信息（脱离服务端也能显示） */
  title: string
  artistText: string
  albumText?: string
  durationMs: number
  coverId?: string
  /** 「来自哪张专辑 / 哪个歌单」，用于分组 */
  source: { kind: 'track' | 'album' | 'playlist'; id?: string; label: string }
  quality: 'original' | 'standard'
  status: 'queued' | 'downloading' | 'paused' | 'done' | 'failed'
  progress?: number
  /** 续传用：DownloadTask.savable() 的序列化结果 */
  resumeState?: unknown
  error?: string
  createdAt: number
  completedAt?: number
}
```

索引文件 `Paths.document/downloads/index.json`，写盘防抖（沿用 `audio-cache.ts` 的 `flushTimer` 模式）。

### 1.6 核心难点：不可播格式怎么办

| 格式类别 | 例子 | 能否直接下原始文件并离线播 |
| --- | --- | --- |
| 原生可播 | flac / mp3 / m4a / wav / aac / alac / aiff / caf | ✅ 可以（白名单见 `player/format-support.ts`） |
| 原生不可播 | wma / ape / dsd… | ❌ 不行 |

不可播格式的问题是：服务端转码产物是 **HLS 分片**（fMP4，2 秒一片），**不能直接当一个单文件下载**。

三个选项：

| 方案 | 做法 | 评价 |
| --- | --- | --- |
| **A. 只支持可播格式** | 不可播格式的下载按钮置灰，说明「该格式需服务端转码，暂不支持离线」 | ✅ **建议采用**：工作量最小、边界清晰 |
| B. 下载后拼接分片 | 拉 m3u8 → 下载全部分片 → 拼接 fMP4 → 封装 | ❌ 需 m3u8 解析 + 分片拼接 + 封装，易错；WMA 只占约 5%，性价比低 |
| C. 下原始文件但离线播不了 | 下载原文件，离线时提示「需联网转码」 | ❌ 等于假离线，最差 |

**建议二期采用 A**，并把这句说明写进 UI —— 否则用户会以为「下载按钮坏了」。

### 1.7 新发现：iOS 备份排除（必须处理，否则有上架风险）

- `Paths.document` 里的文件**会被 iCloud 备份**（这是 iOS 的默认行为，且它正是「系统不会删」的原因之一）
- 但 `expo-file-system` SDK 57 **没有暴露**备份排除能力（已全目录 grep `backup` / `NSURLIsExcludedFromBackupKey`，**无任何匹配**）
- 后果有两个：
  1. 几十 GB 离线音乐进入 iCloud 备份，用户的 iCloud 空间被吃掉
  2. Apple 审核对「可重新下载的数据」有备份排除要求，可能被质疑

**方案**：新增本地原生模块 `modules/file-backup-exclusion`，暴露 `excludeFromBackup(uri)`（内部调用 `NSURL.setResourceValue(NSURLIsExcludedFromBackupKey, true)`）。Android 侧空实现即可（app-specific 目录本来就不参与备份）。

成本可控 —— 项目已有 3 个本地原生模块先例（`airplay-button`、`app-icon`、`system-volume`），照同样结构加即可。**注意：加了本地原生模块必须重跑 `npx expo prebuild`**（见 `apps/mobile/AGENTS.md`）。

### 1.8 下载队列

- 并发上限 **2**（与 `audio-cache` 的 `MAX_PARALLEL_DOWNLOADS` 一致，避免和正在播放的歌抢带宽）
- 队列持久化：`status: 'queued'` 的条目在 App 重启后自动恢复
- 暂停 / 续传 / 取消（用 `DownloadTask` 的对应 API）
- 失败重试：指数退避，超过阈值标记 `failed` 并让用户手动重试
- 网络切换（Wi-Fi ↔ 蜂窝）：需要确认策略。**建议**：蜂窝下载前询问（因为音轨文件很大，FLAC 单曲可到几十 MB）

### 1.9 「已下载」页重做

数据源从 `audioCacheStats()` 改为 downloads 索引：

- **两个数字分开显示**，避免用户混淆：
  - 「离线下载 X 首 · 占用 A GB」（承诺离线）
  - 「播放缓存 Y 首 · 占用 B GB」（不承诺，可随时清）
- 按来源分组（专辑 / 歌单 / 单曲）
- 操作：播放、删除单曲、删除整组、显示占用与可用空间（`Paths.availableDiskSpace` 可用）
- 状态展示：下载中（进度）、暂停、失败（重试按钮）
- 修复现状：`screens/downloaded.tsx` 目前是静态卡、写死「上限 2GB」、不刷新

## 二、外部歌词源（插件化，不内置）

### 2.1 产品定位（按你的要求）

- **我们不内置任何源**
- 只提供「接入能力」：用户自己填 API 信息
- **好处**：无第三方歌词版权风险、无源失效责任、无审核争议
- **代价**：非技术用户门槛高 → 所以**配置流程必须带「测试」与「预览」**（见 2.4）

### 2.2 现成服务调研（供你参考，不内置到 App）

| 服务 | 是否需要凭据 | 形态 | 适合场景 |
| --- | --- | --- | --- |
| **LRCLIB**（lrclib.net） | **不需要**（公开、无需注册、无 API key） | 托管服务 | **最适合做「示例配置」**，因为无凭据门槛 |
| **LrcApi**（HisAtri/LrcApi） | 不需要（有公开 API） | Flask，可 Docker **自建** | 适合「用户自己搭建」的场景 |

**LRCLIB 已核实的关键事实**：

- 端点：`GET /api/get?track_name=&artist_name=&album_name=&duration=`
- 必需 `track_name` + `artist_name`；`album_name` 与 `duration` 强烈建议（提升匹配精度）
- **时长匹配容差 ±2 秒** —— 这是个很好的匹配机制，值得照搬到我们的匹配算法里
- 返回 `plainLyrics`（纯文本）与 `syncedLyrics`（LRC 文本）
- 要求设置 `User-Agent` 标识客户端；超限返回 `429` + `Retry-After`，**必须遵守**；建议请求间隔 200–500ms、串行请求
- `GET /api/search?q=` 最多返回 20 条、不支持分页

> ⚠️ **重要**：LRCLIB 的 `syncedLyrics` 是**整行**级（`[mm:ss.xx]` 行时间戳），**不是逐字**。
> 这意味着：**外部源只能提供 T2（整行）/ T3（纯文本），逐字（T1）只能来自飞牛服务端。**
> 这个事实不影响档位设计，但决定了「外部源无法提升到逐字体验」。

### 2.3 抽象设计：`LyricSourceConfig`

```
LyricSourceConfig {
  id: string
  name: string                    // 用户填，UI 上标注来源用
  enabled: boolean

  request: {
    method: 'GET' | 'POST'
    urlTemplate: string           // 支持占位符
    headers?: Record<string,string>
    query?: Record<string,string>
    bodyTemplate?: string         // POST 用
  }

  auth?: {
    headerName: string            // 如 'Authorization'
    // 凭据本身不写在配置里，存 Keychain；配置只存引用
    credentialRef: string
  }

  response: {
    listPath?: string             // 结果数组位置，如 'data.songs'；不填=响应本身是结果
    syncedPath: string            // 如 'syncedLyrics'
    plainPath?: string            // 如 'plainLyrics'
    titlePath?: string
    artistPath?: string
    durationPath?: string
  }

  format: 'lrc' | 'plain'
}
```

设计要点：

- **占位符**：`{title}` `{artist}` `{album}` `{duration}`（duration 用**秒**，整数，与 LRCLIB 等主流服务一致）
- **凭据与配置分离**：配置（含 URL）存 SecureStore，凭据存 Keychain（复用 `lib/storage.ts` 的 `keyPassword` 模式），避免配置导出时泄露 key
- **取值路径用简化的点号语法**（`data.songs`），**不引入完整 JSONPath 依赖**（保持依赖精简）
- **字段路径可留空**：只填 `syncedPath` 也能工作，降低填写门槛

### 2.4 用户配置流程（「测试」环节是必须的）

```
新增源 → 填表（名称 / URL 模板 / 字段路径 / 可选凭据）
       → 【测试】用当前播放的歌试跑
          显示：匹配到 N 条 · 时长差 X 秒 · 前 3 行预览
       → 确认保存 → 启用
```

**为什么「测试」必须有**：用户填错一个字段路径，结果就是永远拿不到歌词、且完全不知道哪一步错了。没有测试环节，这个功能对非技术用户等于不可用。

### 2.5 修正后的匹配顺序（把外部源插进档位循环）

在原有「档位 × 来源」上，把「来源」从两级扩展为三级：

```
for tier in [逐字, 整行, 纯文本]:
    1. 本地缓存命中        → 用
    2. 飞牛服务端有        → 用 + 写本地缓存
    3. 已启用的外部源有    → 用 + 写本地缓存（并标记来源）
否则 → 显示「暂无歌词」
```

两个性能要点：

- 飞牛服务端**一次请求**就能判定 T1/T2/T3 的服务端部分（`/lyric/list` 返回全部条目）
- **外部源只在服务端完全缺失时才请求** —— 既省流量，也减少对第三方服务的压力（这是对公开服务的礼貌，也避免被限流）

### 2.6 匹配与纠错

- **候选排序**：时长差（越小越好）→ 标题相似度 → 艺术家相似度
- **自动采用阈值**：时长差 ≤ 2 秒 **且** 标题高度相似，才自动采用；否则**进候选列表让用户选**
- **必须有的纠正入口**：「歌词不对 → 换一条 / 重新搜索 / 忽略这个源」
- **UI 必须标注来源**：`歌词来自：{源名称}`，让用户知道这不是服务端提供的
- 标题规范化：去 `feat.` / `ft.` / `(Live)` / `(Remaster)` / `[320K]` 等噪声，统一全半角与大小写（与歌单导入复用同一套规范化函数）

### 2.7 安全与合规

- 凭据存 Keychain；配置导出时自动剔除凭据
- **免责说明**：不保证外部歌词的准确性与合法性，由用户自担（写进设置页说明）
- 请求节流：串行请求 + 200–500ms 间隔 + 遵守 `429` / `Retry-After`（照抄 LRCLIB 的要求，对任何第三方源都适用）
- 尊重你的要求**不内置任何源 URL**；可提供「示例配置」文档 + 一键填入模板，但**必须用户确认保存后才生效**

## 三、新增的待确认项（动手前必须验证）

| # | 待确认 | 为什么重要 |
| --- | --- | --- |
| 1 | **Android 明文 HTTP** | `validateBaseUrl` 允许局域网 `http://`，但 **Android 9+ 默认禁止明文流量** → 必须在 `app.json` 配 `android.usesCleartextTraffic` 或 network security config。**这是 Android 上架的头号阻塞项**（局域网 HTTP 是这个 App 的核心场景） |
| 2 | Android 各原生模块分支 | `airplay-button` 返回 null（预期）；`system-volume` 是桩（需真实现）；`app-icon` 有 activity-alias 实现（需验证真机生效） |
| 3 | `File.createDownloadTask` 的 headers 透传 | 需在 iOS 与 Android 两端分别验证鉴权头是否真正送到服务端（iOS 走 URLSession，可能有额外限制） |
| 4 | iOS 备份排除原生模块 | 确认 `NSURLIsExcludedFromBackupKey` 在当前 RN 新架构下的可用性 |
| 5 | 飞牛 `/track/stream` 是否支持多段 Range | 影响续传效率与断点恢复质量 |
| 6 | 蜂窝网络下载策略 | 是否需要「仅 Wi-Fi 下载」开关（FLAC 单曲可达几十 MB） |

## 四、分期归属更新

| 事项 | 原归属 | 新归属 | 原因 |
| --- | --- | --- | --- |
| Android 补齐 | 四期 | **一期** | 你决定一期同时上架 |
| Android 明文 HTTP 配置 | — | **一期（阻塞项）** | 不配就连不上局域网服务器 |
| `system-volume` Android 真实现 | 四期 | **一期** | 音量条是播放页核心控件 |
| 真离线（下载管理） | — | **二期** | 你决定要做 |
| iOS 备份排除原生模块 | — | **二期** | 真离线的必要配套 |
| 外部歌词源插件化 | — | **二期** | 你决定允许，且需自填 API 的配置体系 |
